# 工序分流与验收批次

> 当前状态见 [STATUS](../STATUS.md)。本文只放现行规则、当前待办和有效决定，过程证据在 `docs/runs/`。
> 精简前全文用 `git show aa126dd:docs/backlog.md` 查看；更早历史见 [backlog-archive](backlog-archive.md)，那里是历史证据，不是现行授权。

## 1. 分工

- **A**：协调与离线开发；需要用户决定时直接 ask；维护队列和共享状态。不设常驻 B，独立研究、实现与审查交给按需子代理。
- **C · 真机验收**：独占设备，只验固定完整 SHA 的构建并保存证据；不改代码，失败回交 A 修复。

## 2. 资源边界

- 单设备独占；每批固定完整 SHA 与对应构建。C 不跟随分支 tip，不在被测 checkout 改代码。
- 队列与共享状态（STATUS、backlog、knowledge）只由 A 整合；C 与子代理只回报增量。
- 跨 worktree 派工须注明实际代码与协调文档的分支及完整 SHA。main 已完成 10-13 整合及 10-14 远端同步，当前队列可从 main 读取。

## 3. 排序原则

- 优先做能减少真机人工、缩短验收的工作。离线通过不替代 ROM、确认卡、App 落地或布局的真机证据。
- **C 队列有未清批次时，A 不新增待真机批次**，只做已授权的离线工作，也不放行未接线的生产路径。
- 每批至多 2–3 个改变真机行为的改动；碰同一确认或布局表面的改动须能独立归因。
- 只读验证不改被测路径时可以搭便车；一次合跑多批时分别固定候选、判据与结论。
- 没有具体目标的“提速/重构”不作为续做理由；要提速，先用当前日志定位具体成本。

## 7. 流转、验证与收尾

### 7.1 回报

回报须带完整代码 SHA 或未提交改动范围；C 另报 run/task、逐腿结论、manifest、台账、cleanup 和持久证据位置。

### 7.2 验证、合并与证据

检查入口见 [离线开发与验证](runbooks/离线开发与验证.md)。

- 改变真机行为的提交：A 报完整 SHA → C 验固定构建 → 通过后只合**验过的 SHA**，不合带后续未验改动的分支 tip。失败则保留改动与运行证据，A 修复成新候选。
- 纯文档改动验证后可独立整合；所在分支祖先夹带未验代码时，只合文档提交。
- 协调文档版本与被测代码 SHA 分别记录。
- 台账无论通过失败都要归集并去重到 main，不等代码通过才收。
- 临时 worktree 回收前，把必要的脱敏证据存到持久位置并核对 manifest。

### 7.3 开跑条件

开跑令不得先于就位报告。就位报告含固定 SHA、唯一设备、设备/姿态/窗口/IME 证据、构建身份与前置检查，且须符合本次候选与授权范围；未知字段不能当通过。
用户沉默不等于回答或批准；“你自己把住”之类的泛化授权不构成提前开跑令，开跑仍须在就位报告之后针对本次候选明确给出。
C 失败即冻结本轮、保留现象/台账/证据并回交 A，不在 C 修代码，也不盲目重跑；C 无任务时回报待命。
手机危险动作的确认见 [AGENTS 铁律 3](../AGENTS.md)：始终由现场用户在设备上操作，任何开发侧授权都不替代。
