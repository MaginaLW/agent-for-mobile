# 设计说明：危险动作风险分级

- 日期：2026-08-01
- 状态：**决策已作出（B 道），待 A 道实现**
- 范围：`SafetyPolicy` 词表分级；**不含**任何免确认路径
- 上游：[危险动作统一硬门](2026-07-19-危险动作统一硬门-design.md)
- 决策入口：[backlog.md](../backlog.md) §4 末节「风险分级 / 任务级额度」

## 0. 一句话结论

**把危险词表拆成「不可逆」与「有撤回窗口」两档，不开任何免确认路径。**
任务级额度本轮**不做**，理由与重开条件见 §4。

## 1. 为什么这件事需要一个决定

原始诉求是「任务级额度」——批准一次、后续同类动作免确认，用来消掉连续危险动作的重复点击。
它与已经写死的东西直接冲突，所以不能由 A 道自行实现：

- 硬门 spec §2 不变量 4：**一次确认只授权当前这一次调用，不生成可重放的通用令牌**
- 硬门 spec §6 非目标：**不实现通用授权令牌或跨会话授权**
- 硬门 spec §3 方案 B（一次性授权令牌）已被明确拒绝，理由是「P0 引入的状态面过大」
- 项目铁律 3：危险操作（发送/支付/删除类）**永远**两段式

## 2. 三个把问题重新定形的事实

### 2.1 「哪些 D 级工具能进额度」是个空问题——D 级工具一个都没在跑

[ToolRegistry.kt:69-288](../../app/gateway/src/main/java/dev/magina/gateway/mcp/ToolRegistry.kt) 注册 25 个工具，
静态 `Level.D` 只有 `notification_reply` 一个，而它的 handler 是 `stub("通知层在 M1b 实现")`，
调用直接抛 `E_CHANNEL_DOWN`，到不了安全门。

真机上弹出的每一张确认卡，**全部来自动态升级**，只有两条路
（[SafetyGate.kt:95-108](../../app/gateway/src/main/java/dev/magina/gateway/core/SafetyGate.kt)）：

| 路径 | 触发条件 |
|---|---|
| `press_key(key=enter)` | 无条件确认 |
| `ui_action(click\|long_click)` | 目标 `text`/`description` 命中词表 |

所以风险分级的对象**不是工具等级表，是这两条动态路上的词表**。

### 2.2 现有词表把两类风险混在一格

```
DANGER_WORDS(17)  删除 清空 移除 卸载 支付 付款 转账 确认交易 立即购买
                  提交订单 注销 退出登录 解绑 修改密码 安装 格式化 恢复出厂
SEND_WORDS(5)     发送 发布 发表 评论 回复
```

上一组做完之后用户自己没有撤销手段；下一组普遍存在撤回窗口。今天两组走完全相同的流程。

### 2.3 额度会拆掉现在真正在防串台的那个机制

现在的门是「确认 → 重读上下文 → 逐字段比对 → 不符报 `E_STALE_REF`」。
额度若在动作发生之前就批掉，**confirm-then-recheck 这个窗口不复存在**，
`PreparedTargetEvidence` / `FocusIdentity` / `InputCommitEvidence` 三段绑定失去挂靠点，要另起一套。

补一条同源顾虑：额度余量是**网关自报状态**。2026-08-01 Deny 腿那次假通过的教训原文是
「自报证据的失败形态长得跟成功一模一样」——余量算错时，外观与正常执行完全一致。

## 3. 决定：两档分级

判据是**用户在动作完成后，能否用自己手上的手段把它撤销**。不看金额、不看动作名。

### I 级 · 不可逆

做完之后用户无自救手段，或撤销成本远高于执行成本。

| 类 | 词 |
|---|---|
| 资金 | 支付、付款、转账、确认交易、立即购买、提交订单 |
| 数据 | 删除、清空、移除、格式化、恢复出厂 |
| 账号与系统完整性 | 注销、退出登录、解绑、修改密码、卸载、安装 |

### II 级 · 有撤回窗口

存在一个明确的、由目标 App 提供的撤回入口，且窗口未过期。

| 类 | 词 |
|---|---|
| 对外发送 | 发送、评论、回复 |
| 对外发表（边界项，见 §3.1） | 发布、发表 |

`press_key(enter)` 不吃词表，按**当前目标会话的性质**定档：私聊/群聊会话 → II 级；
落在 I 级页面上的 Enter（如支付密码框）→ I 级。判定复用 `hasSensitiveSurfaceSemantics`
已有的页面级信号，不新造感知面。

### 3.1 唯一一处我不确定的归档：发布 / 发表

放进 II 级的理由是它们确有撤回入口。但公开发表的撤回**只删得掉副本，删不掉已经被看到这件事**，
这一点弱于私聊撤回。本篇把它放在 II 级并**显式标为边界项**：

- 本轮无实际后果——两档都照常逐次确认，档位只影响卡片措辞。
- 一旦将来有任何方案拿这两档当**免确认资格的键**，这个归档立刻变成承重的，必须重新走 B 道。

### 3.2 分级只影响什么

本篇**只交付分级本身**，不预判它怎么用。已知的下游消费者两个，都不在本篇定：

1. **确认卡措辞与证据强度**——归 [backlog.md](../backlog.md) 批次 2 通知栏审批那篇。
   I 级需要显式的「不可撤销」标注，II 级应当告诉用户撤回窗口有多长；具体呈现由那篇定。
2. **§6 通知卡该展示哪几项证据**——两档直接决定折叠态那一行要说什么，见 §5。

**分级不产出任何免确认路径。** 两档都走完整的确认链，行为与今天逐字一致。

## 4. 明确不做：任务级额度

本轮不引入额度、不引入授权令牌、不引入批准前置。硬门 spec 的不变量 4 与非目标保持原样。

理由不是「额度是错的」，而是**现在缺一个决定它所必需的数据**：
批次 2（通知栏审批）要把单次确认从「盯屏 60 秒」降到「锁屏点一下」。
单次确认降价之后，额度还值不值得引入那一整套状态面，是个当前答不出的问题。
现在定额度是在缺关键数据时拍板。

**重开条件（任一命中就把这条重新写进 backlog §6）：**

1. 批次 2 落地并真机验收通过后，实测单次确认成本仍然高到让连续危险动作不可用；
2. 出现一个真实任务，其危险动作次数多到逐次确认明显荒谬（连发 ≥5 条是个粗略的线）。

重开时的起点不必从零：曾评估过的两个方向记在这里备查——
**(a) 只放发送类、作用域键 = 包名 + 目标会话 label + 工具名，切会话即失效**（复用现有 `PreparedTargetEvidence`，
代价是铁律「发送永远两段式」要改读成「每个目标会话两段式一次」）；
**(b) 批准前置**——派单时大脑先声明本任务的危险动作清单，用户批整份，执行时逐条比对声明与实际，
不符即停（保留强不变量、无可重放令牌，代价是执行器现在没有计划声明这个面）。

## 5. 与 §6 通知卡证据题的关系

backlog §6 待决策首条问「锁屏通知卡展示哪几项证据」，被 A 道的布局方案卡着。本篇给它两个输入：

1. **两档分级本身**就是折叠态那一行最该出现的东西——用户在锁屏上第一眼要判断的是
   「这条要不要立刻展开」，而不是 SHA-256 的前 12 位。
2. **那道题的前提需要 A 道先澄清**：批次 2 定的方案是 full-screen intent，而 full-screen intent
   拉起的是一个 Activity，屏幕空间与现在的 overlay 相同，**不存在放不下 8 项的问题**。
   受限的只有折叠态通知与锁屏摘要行。A 道的布局方案必须把这两层 surface 分开描述，
   否则「8 选 N」这个问法本身是错的。

## 6. 交给 A 道的实现面

1. `SafetyPolicy` 的 `DEFAULT_DANGER_WORDS` / `DEFAULT_SEND_WORDS` 重构为带档位的结构，
   两档词表内容逐字按 §3 落地；`hasSensitiveSurfaceSemantics` 现有的额外词
   （密码、收款、风险、警告）保持在页面级判定里不动。
2. `press_key(enter)` 的档位判定按 §3 末段接页面级信号，不新造感知面。
3. `SafetyDecision.ConfirmationRequired` 增加档位字段，供批次 2 消费；**本轮不改任何确认行为**。
4. 离线用例：两档归档逐词钉住（含 §3.1 边界项，注释写明它是边界项）；
   一条**回归断言**钉住「分级不产出免确认路径」——任一档位下 handler 调用次数在未确认时仍为 0。

## 7. 非目标

- 不引入额度、令牌、批准前置、跨会话授权。
- 不改超时语义（60 秒超时的正解见 backlog §4 批次 2 注脚，属另一篇）。
- 不改敏感 App 黑名单与支付/生物识别不可自动化边界。
- 不改确认卡现有 8 项证据的内容与顺序——那是批次 2 与 §6 的事。
