# 设计说明：危险动作风险分级

- 日期：2026-08-01
- 状态：用户 2026-08-01 决定，两档分级已落地（只产出档位，不改确认行为）；2026-08-02 拍板的执行时机差异见 §3.3，其生产接线未完成，以[语义意图 spec](2026-08-02-语义意图审批-design.md) §5 为准
- 范围：`SafetyPolicy` 词表分级；**不含**任何免确认路径
- 上游：[危险动作统一硬门](2026-07-19-危险动作统一硬门-design.md)
- 决策入口：[backlog.md](../backlog.md) §6；原问题记录见 [backlog 归档](../backlog-archive.md) §6

> 涉及安全姿态的变更须由用户作出真实决定并记录来源；流程调整不构成免确认或放宽硬门的授权。

## 0. 一句话结论

**把危险词表拆成「不可逆」与「有撤回窗口」两档，不开任何免确认路径。**
任务级额度**不做**，理由与重开条件见 §4。

## 1. 背景

原始诉求是「任务级额度」：批准一次，后续同类动作免确认。它与以下已定规则直接冲突，因此只做分级：

- 硬门 spec §2 不变量 4：**一次确认只授权当前这一次调用，不生成可重放的通用令牌**
- 硬门 spec §6 非目标：**不实现通用授权令牌或跨会话授权**；§3 方案 B（一次性授权令牌）已被拒绝
- 项目铁律 3：危险操作（发送/支付/删除类）**永远**两段式

## 2. 分级对象

- 2026-08-01 时静态 `Level.D` 工具只有尚未实现的 `notification_reply`；真机上的确认卡全部来自
  [SafetyGate](../../app/gateway/src/main/java/dev/magina/gateway/core/SafetyGate.kt) 的动态升级：
  `press_key(key=enter)` 无条件确认，`ui_action(click|long_click)` 目标 `text`/`description` 命中词表时确认。
  所以分级对象是**这两条动态路径上的词表**，不是工具等级表。
- 原 `DANGER_WORDS`（17）与 `SEND_WORDS`（5）把「做完无法自救」和「有撤回窗口」混在一起，走同一流程。
- 额度会在动作前批掉，拆掉现有「确认 → 重读上下文 → 逐字段比对 → 不符报 `E_STALE_REF`」窗口；
  额度余量又是网关自报状态，算错时外观与正常执行一样。

## 3. 决定：两档分级

判据是**用户在动作完成后，能否用自己手上的手段把它撤销**。不看金额、不看动作名。

### I 级 · 不可逆

做完之后用户无自救手段，或撤销成本远高于执行成本。

| 类 | 词 |
|---|---|
| 资金 | 支付、付款、转账、确认交易、立即购买、提交订单 |
| 数据 | 删除、清空、移除、格式化、恢复出厂 |
| 账号与系统完整性 | 注销、退出登录、解绑、修改密码、卸载、安装 |

### II 级 · 有撤回窗口

存在一个明确的、由目标 App 提供的撤回入口，且窗口未过期。

| 类 | 词 |
|---|---|
| 对外发送 | 发送、评论、回复 |
| 对外发表（边界项，见 §3.1） | 发布、发表 |

`press_key(enter)` 不吃词表，按**当前目标会话的性质**定档：私聊/群聊会话 → II 级；
落在 I 级页面上的 Enter（如支付密码框）→ I 级。判定复用 `hasSensitiveSurfaceSemantics`
已有的页面级信号，不新造感知面。

### 3.1 边界项：发布 / 发表

放进 II 级是因为确有撤回入口；但公开发表的撤回只删得掉副本，删不掉已被看到这件事，弱于私聊撤回。

- 当前不承重：两档都逐次确认，不影响任何放行判定（2026-08-02 复核仍成立）。
- 一旦有方案拿档位当**免确认资格的键**，这个归档立即承重；须重新向用户说明与铁律的冲突并取得
  明确决定，重开讨论本身不构成免确认授权。

### 3.2 分级只影响什么

本篇只交付分级本身。下游消费者：确认卡与通知的档位措辞（I 级「不可撤销」、II 级撤回窗口），
由[通知栏审批布局 spec](2026-08-01-通知栏审批布局-design.md) 定；以及 §3.3 的执行时机。

**分级不产出任何免确认路径。** 两档都走完整的确认链。

### 3.3 2026-08-02：两档的唯一行为差异是执行时机

用户 2026-08-02 拍板（[语义意图审批 spec](2026-08-02-语义意图审批-design.md) §6 题四）：
审批对象上移到语义意图后，**只有 II 级走「批准后延后执行」**——网关有界等待前台恢复到目标 App，
再重新感知、重新走完整严格链；**I 级批准与执行仍紧挨着**，不进入等待（I 级页面常等不起，
批准一笔转账几分钟后才发生也不可取）。

**两档仍然都逐次确认，分级不产出任何免确认路径。** 差异只落在"批准之后多久执行"，
不落在"要不要人点头"；把"档位有差异"读成"分级开始放宽"是错的。

落地进度以[语义意图 spec §5](2026-08-02-语义意图审批-design.md) 为准：2026-09-07 已有离线基础模块，
**生产接线仍未完成**；不能用基础模块用例宣称延后执行已生效。

## 4. 明确不做：任务级额度

不引入额度、授权令牌、批准前置；硬门 spec 的不变量 4 与非目标保持原样。
理由是缺少决定它所需的数据：单次确认成本降下来之后，额度是否还值得引入整套状态面，当前答不出。

**重开条件（任一命中就把这条重新写进 backlog §6，并由用户重新决定）：**

1. 批次 2 落地并真机验收通过后，实测单次确认成本仍然高到让连续危险动作不可用；
2. 出现一个真实任务，其危险动作次数多到逐次确认明显荒谬（连发 ≥5 条是个粗略的线）。

重开时可参考的两个方向：**(a)** 只放发送类，作用域键 = 包名 + 目标会话 label + 工具名，切会话即失效
（代价：铁律要改读成「每个目标会话两段式一次」）；**(b)** 批准前置——用户批整份危险动作清单，
执行时逐条比对，不符即停（代价：执行器没有计划声明面）。

## 6. 实现面（已落地）

1. `SafetyPolicy` 的 `DEFAULT_DANGER_WORDS` / `DEFAULT_SEND_WORDS` 改为带档位的结构，两档词表逐字按 §3；
   `hasSensitiveSurfaceSemantics` 的额外词（密码、收款、风险、警告）保持在页面级判定里不动。
2. `press_key(enter)` 的档位按 §3 末段接页面级信号，不新造感知面。
3. `SafetyDecision.ConfirmationRequired` 增加档位字段 `riskTier`；本篇不改任何确认行为。
4. 离线用例：两档归档逐词钉住（含 §3.1 边界项并注明）；一条**回归断言**钉住「分级不产出免确认路径」
   ——任一档位下，未确认时 handler 调用次数为 0。

## 7. 非目标

- 不引入额度、令牌、批准前置、跨会话授权。
- 本篇不改超时语义（超时与审批对象见[语义意图审批](2026-08-02-语义意图审批-design.md)）。
- 不改敏感 App 黑名单与支付/生物识别不可自动化边界。
- 不改确认卡现有 8 项证据的内容与顺序。
