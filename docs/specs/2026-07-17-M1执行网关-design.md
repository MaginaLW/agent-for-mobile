# 设计说明：M1 执行器定位升级——多通道 Android 执行网关

- 日期：2026-07-17
- 状态：**草案，待用户审批**（批准前不改主设计、不开工编码）
- 决策人：Magina（用户）
- 证据基础：[主设计](2026-07-16-方向一-手机执行器与订阅大脑-design.md) · [M0 跑测记录](../runs/2026-07-16-M0.md) · [执行 harness](2026-07-17-执行harness-design.md) · knowledge 五册（devices / apps / deeplinks / cost / brain-harness）· 台账 docs/runs/ledger.csv

## 0. 一句话

M1 执行器从「无障碍服务 + 截图 + MCP server」升级为**多通道执行网关**：六级通道按成本从低到高排序（系统 API/CLI → Intent/深链/分享 → 通知 → 无障碍语义树 → 本地 OCR/视觉融合 → 大模型看原图），网关内建自动降级与复核，**能走结构化接口的操作默认不许用截图**。这不是推翻主设计，而是把 cost.md 的可行性结论（"深链库、树优先不是优化项，是可行性前提"）从大脑侧规约下沉为执行器侧机械结构。

## 1. 问题定义（来自 M0/M0.5 实测，非假设）

M0 暴露的核心病灶是**「大脑逐轮看图」循环**：截图 → 模型理解 → 算坐标 → 点击 → 再截图验证。实测代价：

- 纯视觉任务成本高一个数量级：微信类 $3+/任务，Pro 额度只够 ~6 个（cost.md）。任务 2 病态排障烧到 $6.44/186 轮。
- 三类实锤误因：截图 ×3.5 缩放坐标错位（devices.md）、软键盘弹出坐标漂移（2 次误触主因）、页面变化（微信选图器回弹烧 ~10 轮）。
- 中文输入通道死亡：剪贴板戏法被 Android 16 后台限制拦截；预测输入法吞空格（devices.md 两条实锤）。
- `uiautomator dump` 在重动画 app 报 idle 超时（京东）；微信经 uiautomator 通道树恒空（apps.md）。

结论：轮次多、成本高、误触，根因都是**信息在最贵的通道上流动**。M1 的架构任务就是把信息流按通道成本重新分配。

## 2. 与现行设计的冲突与兼容点

逐条对照后结论：**方案与主设计方向一致，是超集扩展，无根本冲突**；有一处职责表述需修订、若干处细化。

| # | 现行设计 | 多通道网关方案 | 判定 |
|---|---|---|---|
| 1 | 主设计 §3：「执行器只做手和眼，大脑只做脑」 | 网关内建通道路由、降级、复核、置信度判断——带上了"反射弧" | **需修订表述**：改为「执行器 = 手 + 眼 + 反射弧（机械策略），大脑 = 规划与决策」。MCP 契约仍是唯一边界，两侧独立可替换的原则不动 |
| 2 | 主设计 §4 工具面 v0（12 个）：a11y-first、ref 寻址、拒绝裸坐标、响应自带状态摘要 | 全部继承并强化；工具数扩到 ~22（§6），`screenshot()` 从一等工具**降级为受控 `screen_capture`（要给理由、优先裁剪）** | 兼容，方向同向加深 |
| 3 | 主设计 §4：`type_text` = a11y SET_TEXT 为主、IME 兜底 | 与本方案第八节完全一致 | 兼容，M0 实锤证明 IME 兜底从"预留"变"必建" |
| 4 | 主设计 §5/§6：技能包（深链、页面地图）放大脑侧 skills/ | 深链注册表、页面指纹、图标模板需要执行器**运行时**用（路由与回退判断） | **细化**：技能包数据拆两半——决策知识（何时用、易错点）留大脑侧 skills/，路由数据（深链表、页面指纹、模板图）编译进执行器技能包，同源维护（见决策点 3） |
| 5 | cost.md 结论：深链/宏/树优先是可行性前提 | 本方案就是该结论的架构化 | 强化 |
| 6 | 执行 harness §5.3：M1 落地 `confirm()` 带内确认，`[AWAIT_CONFIRM]` 保留带外兜底 | 原样采用 | 兼容，接口早已预留 |
| 7 | 执行 harness 站规第 2 条：同一失败手段 ≤2 次（软约束） | 网关机械化执行（`E_RETRY_EXHAUSTED`），站规相应条目降为大脑侧提醒 | 兼容，软约束→机械约束正是 harness §9 预设的升级路径；**站规需出 v3** |
| 8 | 主设计 §9：minSdk 26 | 无障碍截图 API（`takeScreenshot`）要 API 30；先自用、主力机 Android 16 | **修订**：minSdk 提到 30 |
| 9 | 主设计 §10：M1 验收 = 5 任务成功率 ≥ M0 | 保留，另加成本维度：台账加 `executor` 列，新旧链路同任务对比 | 细化 |
| 10 | M0 结论「微信只能视觉」 | 该结论绑定在 **uiautomator 通道**上；自研 AccessibilityService（微信抢红包类工具的存在是旁证）可能读得到微信树 | **必须最先去险**（§11 Spike S1）：若自研 a11y 能读微信，纯视觉任务范围大幅缩小，本设计收益上修 |

## 3. M1 分层架构

```
大脑（Claude Code / Codex CLI，M1 在 PC · M2 迁 Termux）
    │  MCP Streamable HTTP + token（唯一契约，不变）
    │  M1: adb reverse / 局域网 · M2: localhost
┌───▼──────────── 执行网关 App（Kotlin/Compose，minSdk 30）────────────┐
│ L0 网关核心（横切）                                                  │
│    Ktor MCP server · 能力探测(capabilities) · 动作分级/黑名单         │
│    统一响应信封+错误模型 · 同法重试计数器 · 审计 jsonl · 单机单派锁    │
├──────────────────────────────────────────────────────────────────────┤
│ L1 系统通道   Kotlin API（无特权）→ AppOps 授权类 → Shizuku shell 白名单│
│               状态查/改/复核 · 前台app · 键盘态 · 媒体库 · 剪贴板 · 通知│
│ L2 意图通道   深链注册表 · Intent 白名单 · 系统分享 · 执行后前台校验    │
│ L3 通知通道   NotificationListener · 快捷操作 · RemoteInput 直接回复   │
│ L4 UI 通道    自研 AccessibilityService：事件驱动树缓存 · ref/revision  │
│               click/longClick/setText/scroll · 键盘/窗口/前台感知      │
│ L5 视觉通道   a11y takeScreenshot → 本地 OCR → 节点/OCR 融合语义 JSON  │
│               图标模板匹配（技能包资产）· 页面指纹分类                 │
│ L6 兜底       screen_capture(受控原图)：要 reason · 局部裁剪优先        │
├──────────────────────────────────────────────────────────────────────┤
│ 伴生服务：自有 IME（commitText 精确注入，兼作剪贴板读取通道）           │
│           确认层悬浮窗卡片（confirm 工具的 UI 载体）                    │
│ 数据：执行器侧技能包（深链表 · 页面指纹 · 图标模板 · 危险控件词表）      │
└──────────────────────────────────────────────────────────────────────┘
```

**自动降级策略（L0 统一实现）**：每个工具声明自己的通道序列；某通道失败时返回结构化错误（含失败原因 + 是否允许回退 + 建议下一步），**网关内可静默回退的（如深链失败→报错并提示 UI 导航）报错留给大脑决策，纯机械的（如 Kotlin API 拿不到→Shizuku shell）网关内直接换**。同一「工具+参数指纹」失败计数 ≥2 后第三次调用直接拒绝（`E_RETRY_EXHAUSTED`），从机械上终结 $6.44 式磨损。

**坐标主权收归网关**：网关内一切坐标均为物理像素（1260×2800）；裁剪图携带 offset/scale 元数据；模型只见 ref 与 bounds（物理像素，仅供理解布局，不用于点击）。×3.5 缩放坐标错位这一类问题在架构上消灭。

## 4. 统一响应信封与错误模型

所有工具共用一个信封；**每个响应自带执行环境快照 `ctx`**，减少大脑「点完再问在哪」的往返：

```json
{
  "ok": true,
  "data": { },
  "ctx": {
    "app": "com.tencent.mm", "activity": ".ui.LauncherUI",
    "page": "chat|unknown", "revision": 18,
    "keyboard": { "visible": true, "height": 882, "ime": "own|other" },
    "screen": "on", "caps": ["a11y", "shizuku", "notif", "ime"]
  },
  "audit_id": "a-000123"
}
```

```json
{
  "ok": false,
  "error": {
    "code": "E_STALE_REF",
    "message": "ref v18 属 revision 12，当前已是 17",
    "channel": "a11y",
    "retryable": false,
    "fallback": "先 ui_snapshot 刷新再操作"
  },
  "ctx": { }
}
```

错误码枚举（封闭集，大脑可据此写死策略）：

| code | 含义 | 典型 fallback 建议 |
|---|---|---|
| `E_PERM_MISSING` | 缺权限/能力位（附开启指引文本） | 报告用户，人工开启 |
| `E_CHANNEL_DOWN` | 通道不可用（如 Shizuku 未激活） | 网关已自动换通道仍失败时才抛 |
| `E_UNSUPPORTED_KEY` | system_* 的 key 不在白名单 | 无，改用 UI 通道 |
| `E_NOT_FOUND` | 元素/通知/媒体未找到 | ui_snapshot / 滚动查找 / wait_for |
| `E_AMBIGUOUS` | 多个匹配（data 附候选列表） | 大脑挑选后按 ref 精确操作 |
| `E_STALE_REF` | ref 已过期（revision 变了） | ui_snapshot |
| `E_TIMEOUT` | wait_for / 操作超时 | 换条件或报告 |
| `E_VERIFY_FAIL` | 动作已发出但复核不符（附实测值） | 大脑决策：重试/换路/报告 |
| `E_BLOCKED` | 命中敏感黑名单（app/联系人/文件/控件） | 无，报告并停 |
| `E_CONFIRM_REQUIRED` | 危险动作未经确认 | 调 confirm() |
| `E_CONFIRM_TIMEOUT` | 悬浮窗确认超时 | 输出 [AWAIT_CONFIRM] 走带外 |
| `E_RETRY_EXHAUSTED` | 同法失败已达 2 次 | 换通道或收尾报告 |
| `E_LOW_CONFIDENCE` | 视觉融合置信度低 | screen_capture(region) 视觉复核 |
| `E_RATE_LIMITED` | 截图/动作节流 | 稍候（data 附冷却毫秒） |

## 5. MCP 工具面 v1（22 个）

动作级别：**R** 只读 / **W** 普通写（自由+审计）/ **D** 危险（两段式确认）。级别标在工具上是默认值，`ui_action` 等通用工具的实际级别由**目标**决定（命中危险控件词表/敏感黑名单即升 D）。

### 5.1 系统层（L1）

| 工具 | 级别 | 参数 | 返回 data | 实现通道（主→备） |
|---|---|---|---|---|
| `device_info()` | R | — | 物理分辨率/密度/系统版本/能力位/电量 | Kotlin API |
| `system_get_state(key)` | R | key ∈ 白名单枚举：bluetooth, wifi, airplane, battery, network, volume, brightness, screen_lock, do_not_disturb… | `{value, source, cross_checked}` | Kotlin API（BluetoothAdapter/WifiManager/BatteryManager）→ Shizuku `dumpsys` 交叉复核 |
| `system_set_state(key, value)` | W（部分 D） | 可写 key 是**读白名单的子集**（bluetooth, wifi, brightness, volume, do_not_disturb…） | `{applied, verified, actual}` | Shizuku shell 白名单（`svc wifi`、`cmd bluetooth_manager`，Android 16 上哪条有效需实测）→ 失败报错建议 Intent 设置页 + UI 兜底；**内部强制执行后复核**（M0 发现 #2：settings 键不可信，用 dumpsys/API 做真值） |
| `system_verify_state(key, expected)` | R | 同上 | `{match, actual, source}` | 同 get，但走与 set 不同的真值源 |
| `foreground_app()` | R | — | `{package, activity, page_hint}` | 自研 a11y 窗口事件（免 UsageStats 授权）→ Shizuku `dumpsys activity` |
| `keyboard_state()` | R | — | `{visible, height, ime_package}` | a11y windows（TYPE_INPUT_METHOD 窗口） |
| `app_launch(name_or_package)` | W | 名称经技能包解析到包名 | `{launched, foreground_verified}` | Intent LAUNCHER → Shizuku `am start`；执行后前台校验 |
| `app_stop(package)` | W | — | — | Shizuku `am force-stop`（无特权则报 E_CHANNEL_DOWN） |
| `clipboard(op, text?)` | R/W | op ∈ get/set | `{text}` | set: ClipboardManager；get: **自有 IME 焦点通道**（Android 10+ 后台读剪贴板被禁，默认 IME 豁免——自建 IME 的副产品红利） |
| `media_query(type, album?, order?, limit?)` | R | type ∈ image/video/screenshot | `[{uri, name, time, size}]` | MediaStore ContentResolver |

**硬约束：不存在 `shell(command)` 工具。** Shizuku 通道是网关内部实现细节，暴露给模型的只有类型化白名单工具；白名单命令、参数校验、执行后复核、审计全部在工具内部完成。

### 5.2 意图层（L2）

| 工具 | 级别 | 参数 | 返回 data | 实现 |
|---|---|---|---|---|
| `open_uri(uri)` | W | 深链或 https；先查技能包深链注册表 | `{opened, foreground_verified, registry_hit}` | Intent ACTION_VIEW；**执行后必验前台**（OriginOS 深链假成功实锤，devices.md）；失败返回 fallback 提示 UI 导航路径（技能包页面地图） |
| `intent_send(action, uri?, extras?, package?, component?)` | W | action 限白名单（VIEW/SEND/SENDTO/MAIN/设置类 action 枚举）；component 仅接受技能包注册项（如微信 `ShareImgUI`，需实测确认现版本有效） | 同上 | Intent |
| `share_text(text, target?)` / `share_file(uri, mime, target?)` | W | target 为空走系统分享面板 | 同上 | ACTION_SEND；uri 经 FileProvider/MediaStore |

### 5.3 通知层（L3）

| 工具 | 级别 | 参数 | 返回 data | 实现 |
|---|---|---|---|---|
| `notifications_list(package?, limit?)` | R | — | `[{id, app, title, text, time, has_actions, has_remote_input}]` | NotificationListenerService |
| `notification_actions(id)` | R | — | 动作清单 | 同上 |
| `notification_reply(id, text)` | **D**（对外发送） | — | `{sent, verified}` | RemoteInput + PendingIntent.send；⚠️ 微信国内版大概率不带 RemoteInput（待 Spike S5 实测），价值主要在短信/邮件/IM 类国际 app——按低成本顺手实现，不指望它救微信 |
| `notification_open(id)` | W | — | `{opened, foreground_verified}` | contentIntent.send |

### 5.4 UI 层（L4）+ 视觉层（L5/L6）

| 工具 | 级别 | 参数 | 返回 data | 实现 |
|---|---|---|---|---|
| `ui_snapshot(scope?)` | R | scope ∈ interactive(默认)/full/region | `{revision, page_hint, elements:[{ref, role, text, desc, bounds, source, confidence}]}` | **事件驱动缓存**：a11y 监听 WINDOW/CONTENT_CHANGED 持续维护语义树，snapshot 是读缓存不是现场 dump（绕开 idle 等待，京东实锤）；**树空/稀疏时自动融合 OCR**（L5），元素带 `source: a11y|ocr|fused` 与置信度——大脑的心智模型始终是同一份元素列表 |
| `ui_diff(since_revision)` | R | — | 增/删/改元素 + 当前 revision | 缓存树 diff；revision 间隔过大时降级返回全量 |
| `ui_find(text?, role?, desc?, scroll_search?)` | R | scroll_search=true 时网关自己滚动查找（≤N 屏） | 匹配元素列表 | 缓存树查询 + 可选机械滚动 |
| `ui_action(ref, action, params?)` | W（目标定级） | action ∈ click/long_click/set_text/scroll/focus/dismiss | `{done, revision_after, verify}` | ACTION_CLICK 等节点动作为主；ocr 来源的 ref 用 bounds 中心 dispatchGesture；**点击前二次校验**（ref 的文本/位置与缓存一致才出手）+ 危险控件词表拦截（弹出菜单场景实锤：「删除订单」邻位）；set_text 走 SET_TEXT→IME 链（§8） |
| `type_text(text, ref?, mode?)` | W | mode ∈ append/replace；ref 缺省用焦点控件 | `{committed, readback, match}` | §8 输入链：SET_TEXT → 自有 IME commitText；**内置读回验证** |
| `press_key(key)` | W | back/home/recents/enter/del… | — | a11y 全局动作 + IME sendKeyEvent |
| `wait_for(condition, timeout_ms)` | R | condition：text_appears/text_gone/app_foreground/keyboard_shown/hidden/idle | `{met, elapsed, revision}` | 事件驱动等待（不轮询、不烧大脑轮次） |
| `screen_capture(reason, region?|ref?)` | R（受控） | **reason 必填**，枚举：low_confidence/unknown_page/icon_unrecognized/layout_changed/risk_review | `{image(base64), scale, offset, revision}` | a11y takeScreenshot(API 30+，秒级节流)；**给 ref/region 时只回裁剪图**；reason 记审计——事后可查每张原图为什么进了模型 |
| `confirm(action_desc, evidence?)` | — | evidence 可带裁剪图 | `{confirmed | timeout}` | 悬浮窗卡片人工点头（带内）；超时→大脑按 harness §5.1 输出 [AWAIT_CONFIRM] 走带外兜底 |
| `macro_run(name, params)` | 按宏内容定级 | — | — | **占位保留**（工具面预留、返回 E_CHANNEL_DOWN），实现按主设计排 M3 |

## 6. 每层实现选型建议（Kotlin API / a11y / Intent / shell / 本地视觉）

**特权位阶**（L1 内部三级，能力探测上报 `caps`，工具按位阶自动降级）：

1. **普通 App API**（零授权）：BluetoothAdapter/WifiManager 读、BatteryManager、MediaStore、Intent、ClipboardManager 写。
2. **AppOps 授权类**（用户手动开一次）：无障碍、通知使用权、悬浮窗、自有 IME 启用。
3. **Shizuku shell 白名单**（开发期经 adb 启动即可——M1 大脑在 PC，adb 本来就在；M2 起用无线调试自启）：`dumpsys`(状态真值)、`svc`/`cmd`(系统开关)、`am`/`pm`(启停)、`settings put`(含把自己设为默认 IME——`WRITE_SECURE_SETTINGS` 亦可一次性 `pm grant` 拿到，则 IME 切换不再依赖 Shizuku 在线)、`ime enable/set`。

关键选型判断：

- **系统开关写操作离不开 shell 位阶**：Android 13+ 已封死普通 app 编程开关蓝牙（`BluetoothAdapter.disable()` 对 target 33+ 无效）。所以任务 1 的"免 UI"路径以 Shizuku 为前提；Shizuku 不在线时自动降级为「Intent 开设置页 + a11y 点开关」，链路仍通只是慢。
- **截图用 a11y `takeScreenshot`，不用 MediaProjection**：免每次授权弹窗、免前台服务纠缠；节流秒级够用（截图本来就该是低频兜底）。MediaProjection 留给未来连续录屏/宏录制场景。
- **前台 app / 键盘态用 a11y 事件流**，不用 UsageStats（少一个授权面）也不常态用 dumpsys（省 Shizuku 依赖面）。
- **剪贴板读取靠自有 IME**：Android 10+ 只有默认 IME 与焦点 app 可读剪贴板——自建 IME 顺带解锁这条通道，一份投入两份产出。

## 7. 五个 M0 验收任务在新架构下的推荐链路

| 任务 | 推荐链路（通道序列） | 兜底 | M0/M0.5 实测基线 |
|---|---|---|---|
| 1 蓝牙关 | `system_get_state(bluetooth)` → `system_set_state(bluetooth, off)`（内含 dumpsys 复核）——**2 轮、0 截图、全程不碰 UI** | Shizuku 不在线：`open_uri(设置)` + `ui_find/ui_action` 点开关（即 M0 的 7 步 UI 路径，但走缓存树） | 7 步 / ~3min |
| 2 微信发中文 | `app_launch(微信)` → `ui_snapshot`（Spike S1 若证明自研 a11y 读得到微信树则全程结构化；否则自动 OCR 融合）→ `ui_find(文件传输助手)` → `ui_action(click)` → `type_text("中文…", ref=输入框)`（SET_TEXT→IME，读回验证）→ 白名单免确认 → `ui_action(发送)` → `wait_for(text_appears)` 验证上屏 | 聊天列表点击偶发不导航（apps.md）：失败 1 次后改走搜索框路径 | $6.44/186 轮（病态）；ASCII 闭环已通 |
| 3 小红书总结 | `open_uri(xhsdiscover://search/result?keyword=…)`（注册表命中，执行后验前台）→ `ui_snapshot`/`ui_diff` 循环读笔记列表 → 进详情/返回 ×N（`ui_action` 单击纪律：详情页图片区双击=点赞）| 深链失败：UI 导航兜底（技能包页面地图） | ~12 步全通 |

## 8. 中文输入链（M0 第一优先遗留）

三级：**a11y SET_TEXT（首选）→ 自有 IME commitText（兜底）→ 报告失败**。剪贴板粘贴机制彻底废弃（Android 16 实锤已死）。

- 自有 IME：`InputMethodService.currentInputConnection.commitText()` 字面注入——中文/英文/空格/换行/标点一律字面值，**绕开预测引擎**（吞空格、篡改大小写两条实锤同时消灭）；`deleteSurroundingText + commitText` 实现精确覆盖（replace 模式）。
- IME 切换：`WRITE_SECURE_SETTINGS`（一次 `pm grant`）或 Shizuku `ime set`；输入完成可切回用户原 IME（记录并恢复，不打扰日常使用）。
- **验证闭环内置**：`type_text` 提交后读回焦点节点文本（a11y），返回 `{readback, match}`；微信输入框若读不回（树空场景），用 OCR 对输入框区域裁剪验证。

## 9. 本地视觉选型评估

| 方案 | 判定 | 理由 |
|---|---|---|
| **ML Kit Text Recognition v2 中文（bundled 版）——选定起步** | M1b 实现 | 端上运行、bundled 版不依赖 GMS（vivo 国行无 GMS，**必须用 bundled**，APK 增重约 20–40MB）；集成一天量级；识别延迟估计百毫秒级（估算，Spike S3 实测） |
| PaddleOCR mobile（PP-OCRv4/5，ncnn/ONNX） | 备选升级 | 中文精度上限更高、模型 <15MB，但集成成本高一档；仅当 ML Kit 在微信字号/深色模式下精度不达标时启用 |
| 图标模板匹配（技能包资产，NCC/OpenCV 均可，甚至手写） | M1b 小规模 | 每 app 固定几个图标（微信「+」、发送、返回箭头）按物理分辨率归一后模板匹配足够；资产随技能包走 |
| 轻量目标检测（YOLO-n 量化 / UIED 类 UI 检测器） | **暂缓，不进 M1** | 训练+标注+端侧部署成本高；a11y+OCR+模板三层覆盖不住的残余场景要先用台账数据证明存在，再立项 |

融合规则（L5）：a11y 节点为骨架，OCR 文本框按 IoU 挂到节点/补空缺，模板命中生成 icon 元素；输出统一 elements JSON（`source`+`confidence`）。整屏 OCR 结果**网关内缓存按 revision 失效**，页面不变不重跑。

## 10. 权限、ROM 限制、安全与不可实现边界

**权限清单**：无障碍（手动开，vivo 有静默回收风险→前台服务+电池白名单引导+开机自检上报 caps）、通知使用权（手动开）、悬浮窗（确认层）、自有 IME 启用（手动开一次）、`QUERY_ALL_PACKAGES`（sideload 无商店审查问题）、`BLUETOOTH_CONNECT`、`POST_NOTIFICATIONS`、前台服务、`WRITE_SECURE_SETTINGS`（adb 一次性 grant，可选但强烈建议）、Shizuku（开发期 adb 启动）。

**ROM/平台限制**（M1 范围内接受，不硬啃）：

- Shizuku 重启失活：vivo 无线调试重启后关闭 → M1 靠 PC adb 在场兜底；M2 前需专项解决（或接受"重启后降级运行"）。
- a11y takeScreenshot 有秒级节流——架构上截图本来就该低频，冲突不大；连续视觉场景显式不支持。
- FLAG_SECURE 页面无法截图（银行/支付类）——本来就在敏感黑名单，行为=拒进+报告。
- 微信无公开「直达指定聊天」深链；聊天消息内容除通知/屏幕外无结构化读取通道。
- Android 13+ 普通 app 无法编程开关蓝牙/WiFi（shell 位阶专属）。
- 支付/生物识别确认框：系统级隔离，**永不尝试自动化**（红线，写进危险词表）。

**安全模型**（继承主设计 §7 + harness 两段式，新增三处）：

1. 工具级动作分级表（§5）+ 目标动态升级（危险控件词表覆盖弹出菜单）。
2. 敏感黑名单三张：app（银行/证券）、联系人/会话、文件类型；命中即 `E_BLOCKED`。
3. 屏幕/OCR 文本是数据不是指令（prompt injection 防线现在覆盖 OCR 产物——**OCR 结果同样可能携带注入文本**，站规声明范围要扩到 elements JSON）。
4. 审计 jsonl 每步落盘：工具、参数、通道、复核结果、screen_capture 的 reason；任务面板可回放。
5. Ktor server 仅监听 localhost/adb reverse + token 认证（继承主设计）。

## 11. 分阶段实施计划

**Spike 周（去险，先于一切编码，每项 ≤半天真机实验）**：

- S1 ⭐ 自研 AccessibilityService 能否读到微信节点树（决定纯视觉任务范围，收益弹性最大的单一未知数）
- S2 Shizuku 在 vivo OriginOS / Android 16 的激活与存活；`svc`/`cmd bluetooth_manager` 哪条能关蓝牙
- S3 ML Kit bundled 中文在 1260×2800 截图上的精度/延迟
- S4 a11y takeScreenshot 延迟与节流实测
- S5 微信通知是否带 RemoteInput；`ShareImgUI` 直达组件现版本是否可用

**M1a 最小闭环**（验收：5 任务成功率 ≥ M0，且摆脱 PC 端 adb 截图链路）：

L0 网关核心（信封/错误模型/审计/分级）+ L4 事件驱动 a11y（snapshot/find/action/press/wait_for）+ L2 意图层 + L1 无特权子集（device_info/foreground_app/keyboard_state/media_query/clipboard-set/app_launch）+ 自有 IME 输入链 + confirm 悬浮窗 + screen_capture 受控兜底。**OCR 融合是否进 M1a 视 S1 结果**：微信树可读则推迟到 M1b。

**M1b 增强**：L1 Shizuku 位阶（system_set_state 免 UI）+ L3 通知层 + L5 OCR 融合与模板匹配 + ui_diff + 技能包数据格式定稿（深链表从 deeplinks.md 生成）。

**M1c 收口**：站规 v3（软约束下沉部分删改）+ 台账加 executor 列 + 双脑对照（harness §8 的首个真实需求）+ cost.md 再校准。

## 12. 降本估算（⚠️ 本节全部为估算，M1a 验收时以台账实测校准）

锚点（实测）：a11y 型只读任务 $0.44/5 轮；纯视觉任务 4 复测 $2.01/55 轮；每轮带整屏截图是成本主因。

| 任务 | 实测基线 | 新架构估算轮次 | 估算进模型截图数 | 估算成本 |
|---|---|---|---|---|
| 1 蓝牙 | 7 步/~3min | 2–3 | 0 | <$0.1 |
| 2 微信中文 | $6.44/186 轮（病态） | 8–15 | 0–2（S1 乐观则 0） | $0.2–0.6 |
| 3 小红书 | ~12 步 | 8–12 | 0–2 | $0.3–0.6（笔记文本 token 为主，压不掉） |
| 4 截图发微信 | $2.01/55 轮 | 5–8 | 0–1 | $0.15–0.4 |
| 5 京东物流 | 6 步纯视觉 | 6–10 | 0–2 | $0.2–0.5 |

估算依据与不确定性：轮次降幅来自链路结构（任务 4 的相册导航/选图器/坐标排障约 30+ 轮被 media_query+share_file 两轮替代——这部分是结构性的，置信高）；单轮成本按 a11y 型 ~$0.09/轮 锚定（含站规前导，实测）；**微信类的估算强依赖 S1 结果**——若微信树不可读且 OCR 融合精度不足，任务 2/4 仍需 2–5 张裁剪图，成本上限上浮 ~50%。整体目标：纯视觉任务进模型截图数 ↓90%、成本从 $2–3 级降到 $0.3 级（≈ Pro 额度容量从 ~6 任务/月 → 40+ 任务/月，回到原估量级）——**这是目标不是承诺**。

## 13. 开放决策点（请逐条批准或改）

| # | 决策 | 推荐 | 备选 |
|---|---|---|---|
| 1 | Shizuku 定位 | **增强而非依赖**：核心验收链路在无 Shizuku 时全部有降级路径 | 硬依赖（任务 1 免 UI 更稳，但重启失活即瘫） |

| 6 | minSdk 26→30 | 30（takeScreenshot 需要；先自用无兼容包袱） | 26 + MediaProjection 截图（授权弹窗代价） |
