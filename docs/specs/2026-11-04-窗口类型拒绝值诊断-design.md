# 窗口类型拒绝值诊断执行计划

> **For agentic workers:** 遵守委派与工作区规则，独立文件任务并行，强依赖串行，完成独立复审及最终验证。

**Goal:** 在不放宽窗口/IME/拓扑判据、不增加 getter 的前提下，让新的只读诊断结果保留类型范围门已经读到而拒绝的整数及频次。

**Approach:** 先核官方类型约定与既有契约，再按 Kotlin producer、PowerShell consumer/schema、runner 三个不重叠批次并行实现；随后串行专项、完整离线门、独立审查、固定 SHA 及产物 proof。建议并行 3 个实现者（含主协调），共享构建与长测试由 A 串行调度。

**Materials:** [本轮真实诊断](../runs/2026-11-04-诊断后验与窗口采集.md)、[原最小诊断](2026-11-01-窗口清单最小诊断-design.md)、现有 C1b model/probe/controller、严格封套 parser、runner 及其离线用例。原受测完整 SHA 为 `597ca8b713456cbfe82aa84af3abdcb7c19e1c79`；本阶段起点 `90211388f7b585629e353bb25696209fcd542a57`。

**Validation:** 覆盖单次 getter/原短路顺序、负数与大于 255、Int32 两端、重复频次/快照不可变、零项/枚举失败/读取异常、原 observation 字节与阻断结论；严格解析新增字段的键/类型/范围/排序/唯一性/计数及绑定、旧封套拒绝、runner 双产物/隐私/失败不补采。最终运行仓库完整离线门并核固定提交的 APK/proof；不以离线通过宣称 ROM 或 T-L1 通过。

## 依据与非目标

前轮每帧完整枚举 5 项，保存 4、丢弃 1，唯一首次停止为 `window_type_invalid`。生产 adapter 返回非空 Int，因此能确定有一项成功返回的整数越出 `0..255`，但原结果无法恢复具体整数、正负、身份或跨帧关联。

Android 官方 API 的 `getType()` 返回 int；`0..255` 是项目 observation 的边界，不是已核官方范围保证。Android 16 的类型 7 已在当前映射中。AOSP 的默认值与本机实值应区分，不能推断本机就是某个 sentinel 或厂商类型；官方固定版本的来源与范围核查结论随阶段记录归档。

查阅来源及边界：

- [Android API getType](https://developer.android.com/reference/android/view/accessibility/AccessibilityWindowInfo#getType()) 未声明 `0..255` 保证；TYPE_WINDOW_CONTROL=7 是 API 36 新增且项目已有映射。
- [AOSP AccessibilityWindowInfo，android-16.0.0_r1](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/core/java/android/view/accessibility/AccessibilityWindowInfo.java#L99)：mType 初始化/clear 为 -1，getType/setType 与 Parcel 直接传递 int，无该范围检查。
- [同 tag 的 AccessibilityWindowManager](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-16.0.0_r1/services/accessibility/java/com/android/server/accessibility/AccessibilityWindowManager.java#L867) 将 WindowManager 类型映射后传入 setType，转换函数未匹配分支返回 -1。它是 AOSP 参考实现中的具体负值来源，不证明本机实值或 ROM 原因。

上述固定 tag 从 AOSP 官方 GitHub 镜像查阅；本次 Gitiles 工具入口不可达，未假称核过目标 ROM。仓库历史核对表明，该范围随 `174435dc64613fba7c9814295252dfce266b5f27` 的 model/probe/schema 首次同时引入，未找到官方范围引用。

本阶段不扩大该范围、不将越界窗口改为保留、不解释 ROM 根因；不增加窗口 getter、ID、枚举序号、包名、标题、原生错误或图像；不修 opaque 树、不接视觉 producer、不改变运行许可、确认卡及任何动作能力。旧 observation/c1b-v1 及 inventory-result/v1 schema 和原证据保持不变。

## 独立 v2 诊断合同

新 producer 仅输出 `tablet-c1b-inventory-result/v2`。外层仍仅含 schema、observation_json、inventory_frames；内层 observation 继续为冻结的 `tablet-layout-observation/c1b-v1` 原文。

每个 inventory frame 在原字段之外，必须增加 `rejected_type_code_counts` 数组：

| 字段/约束 | 定义 |
|---|---|
| 数组长度 | 0..maximum_windows，硬上限 16；不是逐窗口数组 |
| 每项键 | 仅 platform_type_code、count，两者必填 |
| platform_type_code | Int32 整数，必须小于 0 或大于 255；按数值严格升序、不得重复 |
| count | 整数 1..maximum_windows |
| 守恒 | 所有 count 的和必须等于 first_stop_counts.window_type_invalid |
| 读取来源 | 仅使用原类型 getter 的一次成功返回值；读取异常不新增条目，仍按原首次停止原因计数 |
| 未枚举/无越界 | 必须空数组；枚举失败与成功空清单继续区分 |

Kotlin 在原拒绝点累计直方图，构造结果时复制并排序；不把窗口关联或后续读取带入诊断。消费者拒绝缺字段、额外键、重复/未排序 code、范围内 code、非整数/越界数值、非正 count、容量或和不匹配。该数值表仅解释已有拒绝，不能授予布局或动作能力。

当前新 runner 仅接受 v2，不将 v1 降级/迁移为新结果；历史 v1 以其固定版本解释。新 schema 文件为 `tablet-c1b-inventory-result-v2.schema.json`，原 v1 文件不改。封套文件名升级为 `tablet-c1b-inventory-result-v2.json`；observation 文件名和原文不改。run 收据仍为 `tablet-c1b-run/v2`：字段与含义没有新增，result_schema 显式记录新的封套版本，result_envelope_sha256 继续只指封套原字节。
