# 设计说明：通知栏审批的布局方案

- 日期：2026-08-01
- 状态：呈现层已实现（批次 2）；**通知批准能力已于 2026-08-28 撤销**，现行边界见下方。
  §5 保留 2026-08-01 四条决定及其后续变化
- 范围：批次 2「通知栏审批」的**呈现层**——哪一层 surface 放哪几项证据。锁屏那两条已移出批次 2（§5.4）
- 上游：[危险动作统一硬门](2026-07-19-危险动作统一硬门-design.md) ·
  [危险动作风险分级](2026-08-01-危险动作风险分级-design.md) · [backlog.md](../backlog.md) §4 批次 2、§6

> **2026-08-28 现行安全边界：** Android 的通知 action `PendingIntent` 可被已获通知访问权的
> `NotificationListenerService` 代发，不能作为“真人点头”的证明。因此通知仅保留“拒绝”和
> “查看全部证据”；批准只允许来自已经完成绘制与取证门的可见 `ConfirmOverlay`。拒绝与详情句柄
> 均以 confirmationId 建立唯一 identity，并使用 cancel-current、immutable、one-shot；接收器对
> 任何 `allowed=true` 广播 fail-closed。下文关于通知“允许”或免解锁批准的段落均为历史记录，
> 不授权恢复通知批准。

## 0. 一句话结论

**通知链是三层 surface，别混作一层。** L3（点通知进入的确认页）空间与现有
[ConfirmOverlay](../../app/gateway/src/main/java/dev/magina/gateway/overlay/ConfirmOverlay.kt)
相同，8 项证据全放得下；受限的是**折叠态通知与锁屏摘要行**，那一行放**风险档位与目标**。
通知不承载批准能力。

## 1. 前提

原问法「8 项证据锁屏放不下，选哪几项」不成立：放不下的只有折叠态，且中间还有展开态一层，
不存在"要么一行、要么整页"的二选一。

## 2. 三层 surface 与硬约束

| 层 | 何时出现 | 空间 | 能不能放敏感内容 |
|---|---|---|---|
| **L1 折叠态 / 锁屏摘要行** | 通知一到就有 | 标题 1 行 + 文本 1~2 行 | **不能**。锁屏可见性由系统与用户控制，明文预览会暴露给任何拿起手机的人 |
| **L2 展开态通知**（`BigTextStyle`） | 用户下拉展开 | 多行文本 + 最多 3 个 action button | 有限。仍在通知栏，仍可能在锁屏上展开 |
| **L3 确认页** | 用户点通知进入 | 与现有 overlay 相同 | 能，即确认卡的等价物 |

### 2.1 `USE_FULL_SCREEN_INTENT`：不声明

Android 14+ 起该权限只对通话/闹钟类应用默认授予。**决定二（§5）：不声明 FSI**，通知停在 L2，
用户点进 L3。FSI 的作用是把整页免解锁糊到锁屏上，与 L1 用 `VISIBILITY_PRIVATE` 挡住明文直接冲突，
所以不声明是与 L1 自洽的选择，不是降级。[AndroidManifest.xml](../../app/gateway/src/main/AndroidManifest.xml)
刻意不声明并附注释。平台行为判断未经真机确认；验收应确认没有任何路径依赖 FSI。

### 2.2 独立通知通道

[GatewayService](../../app/gateway/src/main/java/dev/magina/gateway/GatewayService.kt) 的前台服务通道
`CHANNEL_ID = "gateway"` 是 `IMPORTANCE_LOW`。**审批走新的独立 `IMPORTANCE_HIGH` 通道**：
混用会让审批通知不响、不浮窗，且用户关掉前台服务通道时会连审批一起关掉而不自知。

## 3. 每层放什么

### 3.1 L1 折叠态 / 锁屏摘要行

一行，`[档位] · [动作] → [目标]`：

```
不可逆 · 点击「确认交易」 → 支付宝
可撤回 · 发送消息 → 文件传输助手
```

- **档位排第一**：用户第一眼要判断"这条要不要立刻展开"，档位是唯一能回答这个问题的字段
  （[风险分级 spec](2026-08-01-危险动作风险分级-design.md) §5 同一结论）。
- **明确不放**：明文预览、输入 SHA-256、参数指纹、焦点几何。前者是隐私，后三者对人没有判断价值。
- 用 `VISIBILITY_PRIVATE` + `setPublicVersion()`：锁屏只显示脱敏版本，解锁后才显示完整。
- 档位来自 `SafetyDecision.ConfirmationRequired.riskTier`，不新造感知面。

### 3.2 L2 展开态通知

- 文本区：**三项锚点**——档位、目标会话、明文预览（决定一）。明文预览进通知栏是用户接受的隐私让步。
  前台包与目标会话冗余；预览超长截断处补 `…`，截断本身可见，所以不另放长度。
- action button：**只有「拒绝」与「查看全部证据」**（进 L3）。原「允许」已于 2026-08-28 撤销。

### 3.3 L3 确认页

现有 8 项证据原样搬过去，不改内容与顺序（[风险分级 spec](2026-08-01-危险动作风险分级-design.md) §7）。
唯一增量是档位标注：I 级显式「不可撤销」，II 级给出撤回窗口时长。

## 4. 与硬门的接缝

1. **审批通道大脑碰不到**（backlog §4 批次 2 红线）。用户回执直接进网关自己的 receiver，
   句柄与 `confirmationId` 绑定且一次性；审批凭据与大脑用的 gateway token 分离；
   `TestControl` 不携带、也不能设置真人决定。
2. **只能有一个决定生效。** `ConfirmOverlay` 与通知共用同一个 future / CAS，第一个到达的决定赢，
   另一条立刻失效；通知侧只能产生拒绝。
3. **人机延迟导致 `E_STALE_REF`** 是本篇不解的已知代价；处置见 §5.3（安全失败即终态），
   根本解法是把审批对象上移到语义意图，见[语义意图审批 spec](2026-08-02-语义意图审批-design.md)。

## 5. 四条决定（用户 2026-08-01 拍板）及后续变化

| # | 决定 | 落点 | 现行状态 |
|---|---|---|---|
| 一 | L2 展开态放**三项锚点**：档位 + 目标会话 + 明文预览 | `ConfirmNotificationContent.expandedText` | 有效 |
| 二 | **不声明** `USE_FULL_SCREEN_INTENT`，通知停在 L2、点进 L3 | AndroidManifest（刻意缺席，附注释） | 有效 |
| 三 | 锁屏「允许」全部免解锁（两档均可） | `setAuthenticationRequired` 保持默认 false | 历史明示选择；**通知批准已于 08-28 撤销**，见 §5.5 |
| 四 | ~~批准后 `E_STALE_REF` 限次重弹，最多 2 次~~ | `StaleReconfirmGuard` 降为纵深防御 | **已作废**（2026-08-02），安全失败即终态，见 §5.3 |

决定的原始拍板记录见[拍板记录](2026-08-01-通知栏审批布局-B道拍板.md)。

### 5.1 决定三当时接受的风险

当时被接受的是：任何拿到手机的人都能在确认窗口内免锁屏密码替用户批准危险动作；
审批通道红线挡的是大脑，挡不到物理接触。该选择从未被行使（§5.4），且已被 08-28 撤销通知批准所覆盖。

### 5.2 决定二 + 决定三的组合

不声明 FSI + L1 `VISIBILITY_PRIVATE` 意味着：若在锁屏上批准，用户只看得到 L1 那一行，三项锚点要解锁
展开才出现。这只是历史方案的推论，不是当前验收项。

### 5.3 决定四已作废：安全失败即终态（2026-08-02 重新拍板）

原「限次重弹」的前提是重弹可达，但重弹要靠大脑再调一次工具；站规
[gateway-executor-preamble.md](../../scripts/prompts/gateway-executor-preamble.md) §4 规定安全失败是终态，
`E_STALE_REF` 与 `E_CONFIRM_REQUIRED` 都在终态码里，**不得重试同一危险动作、不得输出 `[AWAIT_CONFIRM]`**，
所以计数器连 1 都到不了。

**决定：维持站规，不开有界重试的口子。** 落地三条：

1. 耗尽路径的 fallback 不再输出 `[AWAIT_CONFIRM]`，按站规报告「结果：失败」；措辞放在纯 Kotlin 常量并由离线用例钉住。
2. `StaleReconfirmGuard` 保留但只作纵深防御，类注释写明当前走不到；它不构成重试资格。
3. 站规与腿模板一字未改，不新增任何重试口子或第二腿。

**已知并接受的代价**：`E_STALE_REF` 一发生，用户就白批一次，须从头再来。批次 2 验收判据 3
（连续两次 stale 后停在 `[AWAIT_CONFIRM]`）**永远记「未触达」**，不许为了让它变绿而扭曲流程。

### 5.4 锁屏那两条已移出批次 2：与 D1 结构性冲突（2026-08-02 用户拍板）

| 移出项 | 原属 | 现状 |
|---|---|---|
| 锁屏免解锁批准 | 判据 1 的一半 | 未验证，且当前跑不通；通知批准已于 08-28 撤销 |
| 锁屏只显示脱敏行（`VISIBILITY_PRIVATE` + `setPublicVersion`） | §3.1 | 未触达——通知从未在锁屏上出现过 |

**冲突的性质**：`press_key` 是 W 级，`SafetyGate.execute` 先做 `requireKnownForeground`，早于
`policy.assess`；锁屏后 `applicationWindow()` 为 null，调用在 `E_BLOCKED` 结束，**确认卡与审批通知都不会出现**。
既有用例 `SafetyGateTest.unknown foreground blocks Level W/D before confirmation and execution` 以
`confirmerCalls == 0` 钉住。另外确认卡是 `TYPE_APPLICATION_OVERLAY`，不显示在 keyguard 之上。

这是 D1 按设计工作：**不放宽 `requireKnownForeground`，不给 keyguard 开特例。**

**重开条件（任一成立）**：

1. 语义意图审批生产接线落地——批准对象是意图，执行前重新感知并走完整严格链，前台须重新可知；
2. 出现一条不放宽任何证据要求、又能在锁屏下建立可信前台身份的路径（目前不知道有）。

重开时两条按原样验，不许因"当初没验过"默认成立；且**重开不恢复通知批准**，批准仍只来自满足页首
08-28 边界的可见 `ConfirmOverlay`。

### 5.5 决定三当前没有实际后果

决定三从未产生可观察后果（§5.4 锁屏审批走不通），08-28 后通知也不再有「允许」action。
`setAuthenticationRequired` 的默认值是历史明示选择留下的痕迹，**不是漏设、也不是恢复通知批准的依据**。
将来若有任何方案重新引入通知批准，须另行设计、满足页首 08-28 边界并由用户重新决定，
不能凭决定三或语义意图落地恢复。

## 6. 非目标

- 不留任何危险动作重试口子（§5.3）。
- 本篇不改超时语义、不改现有 8 项证据的内容与顺序、不改硬门任何不变量。
- 不引入额度或授权令牌（[风险分级 spec](2026-08-01-危险动作风险分级-design.md) §4 已定）。
