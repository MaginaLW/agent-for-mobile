# 设计说明：通知栏审批的布局方案

- 日期：2026-08-01
- 状态：**已拍板并实现**（四条决定见 §5；拍板记录 `2026-08-01-通知栏审批布局-B道拍板.md`）
- 范围：批次 2「通知栏审批」的**呈现层**——哪一层 surface 放哪几项证据
- 上游：[危险动作统一硬门](2026-07-19-危险动作统一硬门-design.md) ·
  [危险动作风险分级](2026-08-01-危险动作风险分级-design.md) · [backlog.md](../backlog.md) §4 批次 2、§6

## 0. 一句话结论

**两层 surface 别混作一层。** full-screen intent 拉起的是 Activity，空间与现在的
[ConfirmOverlay](../../app/gateway/src/main/java/dev/magina/gateway/overlay/ConfirmOverlay.kt)
一样大，现有 8 项证据全放得下、一项都不用删；真正受限的是**折叠态通知与锁屏摘要行**，
而那一行该说的是**风险档位与目标**，不是 SHA-256 的前 12 位。

需要你拍板的只剩两处，都在 §5：中间那层「展开态通知」放几项；以及 full-screen intent
权限没授予时怎么降级。

## 1. 先纠正提问的前提

§6 原来的问法是「8 项证据锁屏放不下，选哪几项」。B 道 2026-08-01 指出这个前提不成立，
本篇按更正的前提重写：**放不下是折叠态的事，不是 full-screen intent 的事。**

顺带纠正一个更细的错误——这条链其实是**三层**，不是两层。把中间那层漏掉，就会得出
"要么一行、要么整页"的假二选一。

## 2. 三层 surface 与它们各自的硬约束

| 层 | 何时出现 | 空间 | 能不能放敏感内容 |
|---|---|---|---|
| **L1 折叠态 / 锁屏摘要行** | 通知一到就有 | 标题 1 行 + 文本 1~2 行 | **不能**。锁屏可见性由系统与用户控制，明文预览会直接暴露给任何拿起手机的人 |
| **L2 展开态通知**（`BigTextStyle`） | 用户下拉展开 | 多行文本 + **最多 3 个 action button** | 有限。仍在通知栏，仍可能在锁屏上展开 |
| **L3 full-screen intent 拉起的 Activity** | 高优先级通知直接全屏拉起，或用户点通知进入 | 与现有 overlay 相同 | 能。这就是现在确认卡的等价物 |

### 2.1 一条会咬人的工程约束：Android 14+ 的 `USE_FULL_SCREEN_INTENT` 不再自动授予

本机是 Android 16、`targetSdk = 35`。从 Android 14（API 34）起，该权限**只对以通话/闹钟为
核心功能的应用默认授予**；其余应用安装后默认是 denied，要用户自己去系统设置里开
（`Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT`）。而当前
[AndroidManifest.xml](../../app/gateway/src/main/AndroidManifest.xml) **根本没有声明这个权限**。

后果不是"做不了"，而是：**方案必须在拿不到 full-screen intent 时也成立**。拿不到时
通知停在 L2，用户点一下进 L3，多一次点击但链路不断。这也正是 §5 第二道选择题的由来。

> 这条约束我没上真机验证过（本会话不碰真机）。它来自平台行为而非本仓代码，
> 批次 2 真机验收时应当**先单独确认这个开关的实际状态**，再判断降级路径有没有被走到。

### 2.2 已有的通知面

[GatewayService](../../app/gateway/src/main/java/dev/magina/gateway/GatewayService.kt) 已建了
`CHANNEL_ID = "gateway"`、`IMPORTANCE_LOW` 的前台服务通道。**审批必须走新的独立通道**
（`IMPORTANCE_HIGH`）：前台服务那条是常驻低优先级的，混在一起会让审批通知不响、不浮窗，
而且用户一旦嫌吵关掉整个通道，会连审批一起关掉而不自知。

## 3. 每层放什么

### 3.1 L1 折叠态 / 锁屏摘要行——只有一个合理答案，不构成选择题

一行，`[档位] · [动作] → [目标]`：

```
不可逆 · 点击「确认交易」 → 支付宝
可撤回 · 发送消息 → 文件传输助手
```

- **档位排第一。** 用户在锁屏上第一眼要判断的是"这条要不要立刻展开"，档位是唯一能回答
  这个问题的字段（[风险分级 spec](2026-08-01-危险动作风险分级-design.md) §5 同一结论）。
- **明确不放**：明文预览、输入 SHA-256、参数指纹、焦点几何。前者是隐私（那是要发出去的
  消息正文），后三者在锁屏上对人没有任何判断价值。
- 实现上用 `VISIBILITY_PRIVATE` + `setPublicVersion()`：锁屏只显示脱敏版本，解锁后才显示完整。

**档位字段已经就绪**：`SafetyDecision.ConfirmationRequired.riskTier`（本会话已实现，
只产出不消费），批次 2 直接读即可，不需要再造感知面。

### 3.2 L2 展开态通知——真正需要你拍板的地方

3 个 action button 的上限对我们是宽裕的：允许 / 拒绝两个就够，第三个位置可以留给
「查看全部证据」（进 L3）。争议在**文本区放几项**。

| 选项 | 放什么 | 换来什么 | 代价 |
|---|---|---|---|
| **A · 三项锚点** | 档位、目标会话、明文预览 | 常见场景（发消息）在通知里就能判完，不用进 L3——这是批次 2 全部收益所在 | 明文预览进了通知栏；证据强度弱于确认卡 |
| **B · 五项** | A + 输入长度 + 前台包 | 长度能挡住"预览被截断后看不出还有一大段"这类攻击面 | 五行文本在展开态已经偏长，用户大概率不逐行读 |
| **C · 零项** | 只有档位 + 一句「必须展开核对」 | 证据强度与今天完全相同，一步不让 | 每次都要进 L3，批次 2 想消掉的那次点击原样还在 |

我的倾向是 **A**，理由是批次 2 的目的就是把"盯着屏幕 60 秒"降成"锁屏上点一下"，
C 等于把这个目的取消掉；而 B 多出的两项在真人实际判断里权重很低。
但**明文预览进通知栏是个真实的隐私让步**，这一步得你点头，不该由 A 道自行决定。

### 3.3 L3 Activity——8 项原样搬过去，不删减

[风险分级 spec](2026-08-01-危险动作风险分级-design.md) §7 已经写死：不改确认卡现有 8 项
证据的内容与顺序。L3 与现有 overlay 空间相同，照搬即可。**唯一的增量是档位标注**：
I 级需要显式的「不可撤销」字样，II 级应当告诉用户撤回窗口有多长——这一条本来就归批次 2。

## 4. 与硬门的三条接缝（不需要拍板，但方案不自洽就不能实现）

1. **审批通道必须让大脑碰不到**（backlog §4 批次 2 红线）。action button 的 `PendingIntent`
   只能回网关自己的 receiver，且必须带与 `confirmationId` 绑定的一次性 nonce——否则一个能
   构造 Intent 的第三方就能替人点「允许」。审批凭据与大脑用的 gateway token 分离。
   `TestControl` 那句"不携带、也不能设置真人决定"是同一条理由。

2. **两条通道并联，只能有一个决定生效。** `ConfirmOverlay.ask()` 与通知审批必须共用同一个
   future / CAS：第一个到达的决定赢，另一条立刻失效。否则会出现"卡上点了拒绝、通知上点了
   允许"这种两个真人决定互相打架的状态——而 Deny 腿那次假通过已经证明，这类状态的失败形态
   长得跟成功一模一样。

3. **通知路径必然把人机延迟拉长，`E_STALE_REF` 会更常见。** 确认前后要求证据逐字段相等，
   人从锁屏拿起手机、解锁、展开、点击，比盯着屏幕点一下慢得多。这是**已知代价，本批次不解**：
   60 秒超时的正解不是调大数值，而是把审批对象上移到语义意图、批准后重新走一遍严格链
   （backlog §4 批次 2 注脚，属另一篇 spec）。批次 2 真机验收时应当把这一项当成**预期观察**
   而不是缺陷记录下来。

## 5. 四条决定（用户 2026-08-01 经 AskUserQuestion 拍板）

| # | 决定 | 落点 |
|---|---|---|
| 一 | L2 展开态放**三项锚点**：档位 + 目标会话 + 明文预览 | `ConfirmNotificationContent.expandedText` |
| 二 | **不声明** `USE_FULL_SCREEN_INTENT`，通知停在 L2、点进 L3 | AndroidManifest（刻意缺席，附注释） |
| 三 | 锁屏「允许」**全部免解锁**（两档均可） | `ConfirmNotifier.allowAction`，`setAuthenticationRequired` 保持默认 false |
| 四 | 批准后 `E_STALE_REF` **限次重弹，最多 2 次**，超过按 `[AWAIT_CONFIRM]` 停下 | `StaleReconfirmGuard` |

B 道对原两道题的改动：题一删掉「前台包」（与"目标会话"冗余）与「输入长度」（预览截断处会补 `…`，
"有没有被截"本来就看得见）；题二重新定框——FSI 的作用正是把整页**免解锁**糊到锁屏上，
而 L1 刚决定用 `VISIBILITY_PRIVATE` 把明文挡在锁屏外，**两者直接冲突**，所以真正的问题是
"要不要声明"，答案是不声明。这不是降级，是与 L1 自洽的正解。

### 5.1 决定三是一次「已知并接受的风险」，不是遗漏

被接受的是：**任何拿到这台手机的人，都能在 60 秒确认窗口内替用户批准一笔转账、一次删除、
一次改密码，不需要锁屏密码。** 批次 2 的红线（审批通道让大脑碰不到）挡的是大脑，挡不到物理接触。

换来的是收益完整兑现：任何危险动作都是锁屏上一次点击。**重开条件**：手机曾离开用户控制，
或出现一次真实误批准；届时最小改动是按 `riskTier` 给 I 级挂 `setAuthenticationRequired(true)`，
接口已就位。代码注释里写明了这是明示选择并指向拍板记录——**免得将来被当成漏设的默认值"顺手修掉"**。

### 5.2 决定二 + 决定三组合出的必然结果

不声明 FSI + L1 用 `VISIBILITY_PRIVATE`，两条叠加意味着**免解锁批准时用户实际读到的证据
只有 L1 那一行**（`[档位] · [动作] → [目标]`），三项锚点要解锁展开才出现。

这不是缺陷，也没有免费的修法：要让免解锁批准也看到三项，只能把明文预览放进 public version，
即放上锁屏——那正是 §3.1 排除掉的。**稳定形态就是「锁屏一行批准，想看证据就解锁」**。
C 道验收时按**预期行为**核对，不要当证据缺失记录。
