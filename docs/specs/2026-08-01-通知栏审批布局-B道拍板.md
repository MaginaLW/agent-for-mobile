## 2. 决定三是一次「已知并接受的风险」，不是遗漏

B 道的推荐是「I 级要解锁、II 级不要」，用户**明确选择了全部免解锁**。如实记录被接受的是什么：

> `Notification.Action` 的 `setAuthenticationRequired` 保持默认 false。
> **任何拿到这台手机的人，都能在 60 秒确认窗口内替用户批准一笔转账、一次删除、一次改密码，
> 不需要用户的锁屏密码。** 批次 2 的红线（「审批通道必须让大脑碰不到」）挡的是大脑，
> 挡不到物理接触，这条风险不在原红线覆盖范围内。

换来的是批次 2 的收益完整兑现：任何危险动作都是锁屏上一次点击。

**重开条件**（任一命中就重新写进 backlog §6）：手机曾离开用户控制（丢失、借出、被他人长时间持有）；
或出现一次真实的误批准。届时最小改动是把 `setAuthenticationRequired(true)` 按 `riskTier` 挂到 I 级上——
接口已就位，改动量很小，**所以现在选宽松不会把路堵死**。

### 2.1 决定二与决定三组合出的必然结果：锁屏上批准时看到的是一行，不是三项

不声明 FSI（决定二）+ L1 用 `VISIBILITY_PRIVATE` + `setPublicVersion()`（方案本体 §3.1 已定，明文不上锁屏），
两条叠加意味着**免解锁批准时用户实际读到的证据只有 L1 那一行**（`[档位] · [动作] → [目标]`），
决定一的三项锚点只在解锁后展开通知时出现。

这不是缺陷、也没有免费的修法：要让免解锁批准也看到三项，只能把明文预览放进 public version，
即放上锁屏——那正是 §3.1 排除掉的。**稳定形态就是「锁屏一行批准，想看证据就解锁」**，
按此实现，不再往复。

C 道验收时应当把这条当**预期行为**核对，而不是当证据缺失记录。

## 3. B 道对 A 道两道原题的改动（供 A 道对齐）

**题一**：A 道原 B 选项是「三项 + 输入长度 + 前台包」。前台包与「目标会话」冗余，删掉；
长度单独成项后重新评估——预览有 `PREVIEW_LIMIT = 64`（[InputCommitEvidence.kt:29](../../app/gateway/src/main/java/dev/magina/gateway/core/InputCommitEvidence.kt)），
超长截断**但截断处补 `…`**，所以「有没有被截」本来就看得见，长度只多告诉用户「还剩多少」。
A 道「权重很低」的判断方向对、理由不准，最终仍选三项。

**题二**：A 道把这题框成「拿不到权限怎么降级」。B 道认为框错了——FSI 的作用正是把整页**免解锁**
糊到锁屏上，而 L1 刚决定用 `VISIBILITY_PRIVATE` 把明文挡在锁屏外，**两者直接冲突**。
所以真正的问题是「要不要声明」，答案是不声明；这不是降级，是与 L1 自洽的正解。
顺带省掉一条需要用户去系统设置手动打开的依赖。

## 4. 三条硬门接缝的归类复核（A 道方案本体 §4）

| 接缝 | A 道归类 | B 道复核 |
|---|---|---|
| 1 · 审批回执一次性 nonce、凭据与 gateway token 分离 | 不需拍板 | **归类正确**，纯机械安全要求，无取舍面 |
| 2 · overlay 与通知共用同一个 CAS，先到者赢 | 不需拍板 | **归类正确**，纯正确性 |
| 3 · 人机延迟拉长使 `E_STALE_REF` 更常见 | 不需拍板，验收时当预期观察 | **归错了**，已提成题四并作出决定 |

### 4.1 接缝 3 为什么藏着用户的决定

两条错误路径的兜底是不对称的：

- 超时 `E_CONFIRM_TIMEOUT` → fallback `输出 [AWAIT_CONFIRM] 暂停报告，走带外两段式`
  （[ConfirmOverlay.kt:308](../../app/gateway/src/main/java/dev/magina/gateway/overlay/ConfirmOverlay.kt)）
  → 大脑**停下报告**。
- 批准后 stale `E_STALE_REF` → fallback `重新感知当前页面和目标后再发起一次新调用`
  （[SafetyGate.kt:342](../../app/gateway/src/main/java/dev/magina/gateway/core/SafetyGate.kt)）
  → 大脑**被明确指示再来一次** → 再弹一张卡 → 用户再批一次。**无次数上限。**

今天这条路几乎不触发（人盯着屏幕，2 秒点完）。通知审批把窗口拉到十几秒至一分钟，
目标 App 期间来一条新消息就足以让证据不再逐字段相等。所以批次 2 会顺带上线一个
「批准 → 失败 → 再批准」的无界循环——**不选也是选**，因为现状会随批次 2 一起发货。

### 4.2 决定四的实现约束

最多重弹 2 次，第 3 次直接按 `[AWAIT_CONFIRM]` 停下报告。**计数键不能用参数指纹**：
`press_key(enter)` 的参数恒为 `{key:"enter"}`，指纹跨重试完全相同，会把不相干的两次动作并成一次；
`ui_action` 的 `ref` 则在重新感知后必变，又会把同一个语义动作拆成两次。

建议的键是「工具名 + 目标会话 label + 档位」，配一个短 TTL（一次成功、或一段静默后清零）。
**这个键的确切定义归 A 道判断**，B 道只钉三条不变量：

1. 计数**不得**把两个不同的语义动作并成一次（否则第二个动作会莫名其妙被拒）；
2. 计数**不得**把同一个语义动作的重试拆成多次（否则限次形同虚设，退化回无界循环）；
3. 停下时走的是 `[AWAIT_CONFIRM]` 暂停报告，**不是**静默放弃——用户必须知道自己批准过的事情没做成。

## 5. 交给 A 道的实现面

1. **L1**：一行 `[档位] · [动作] → [目标]`；`VISIBILITY_PRIVATE` + `setPublicVersion()`；
   明文预览 / SHA-256 / 参数指纹 / 焦点几何一律不出现在 public version。
2. **L2**：`BigTextStyle`，文本区三项锚点（档位、目标会话、明文预览）；
   action button 三个——允许 / 拒绝 / 查看全部证据（进 L3）。
3. **L3**：现有 8 项原样搬过去，唯一增量是档位标注（I 级显式「不可撤销」字样，
   II 级给出撤回窗口时长）。消费 `SafetyDecision.ConfirmationRequired.riskTier`（`549b6d3` 已就位）。
4. **权限**：`USE_FULL_SCREEN_INTENT` **不声明**。审批走**新的独立 `IMPORTANCE_HIGH` 通道**，
   与现有 `CHANNEL_ID = "gateway"` 前台服务通道（`IMPORTANCE_LOW`）分开——
   否则用户嫌吵关掉整个通道会连审批一起关掉而不自知。
5. **锁屏授权**：`setAuthenticationRequired` 保持默认 false（决定三）。
   代码注释须写明这是**明示选择**并指向本篇 §2，避免将来被当成漏设的默认值「顺手修掉」。
6. **限次重弹**：按 §4.2 三条不变量实现。
7. **接缝 1 / 2 照方案本体 §4 实现**：一次性 nonce + 凭据分离；overlay 与通知共用同一个 CAS。

## 6. 非目标

- 不改超时语义（60 秒不动；正解是把审批对象上移到语义意图，属另一篇 spec）。
- 不改现有 8 项证据的内容与顺序。
- 不引入额度或授权令牌（[风险分级 spec](2026-08-01-危险动作风险分级-design.md) §4 已定）。
- 不改硬门任何不变量。

## 7. 留给 C 道验收的三条

1. **免解锁批准确实可用**，且锁屏上呈现的是脱敏版本（无明文预览）——决定三与 §2.1 的直接后果。
2. **`USE_FULL_SCREEN_INTENT` 的实际状态**：本篇选择不声明，验收应确认没有任何路径依赖它。
   A 道对该权限「Android 14+ 不再自动授予」的判断来自平台文档，**未经真机确认**。
3. **限次重弹的边界**：连续两次 stale 后第 3 次确实停下并输出 `[AWAIT_CONFIRM]`，
   而不是静默放弃或继续无限重弹。
