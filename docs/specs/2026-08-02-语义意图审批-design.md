# 设计说明：把审批对象从「证据快照」上移到「语义意图」

- 日期：2026-08-02
- 状态：**四题已拍板（§6）；§5 的 A 道离线部分已实现，但默认关着**——`SafetyGate` 的
  `intentApproval` 参数不给就是今天的行为一字不变。**切换到这条路径是安全姿态变更，
  必须走真机验收批次**；开关关着时这段代码只被离线用例执行到，那是有意的分阶段落地
- 范围：危险动作确认链的**审批对象**与**执行前校验**；不改感知面、不改工具面、不改站规

## 0. 一句话结论

**人批准的应该是「往文件传输助手发这条消息」，不是「windowId=42、bounds=[302,2637,957,2727]、
IME 会话 id=…… 这一组当时的读数」。** 把审批对象上移到语义意图之后，执行前的校验**一条都不减**
——重新感知、重新走完整严格链，只是这次拿新证据去比**意图**，而不是比批准那一瞬间的实现细节。

由此顺带解决三件今天解决不了的事：人机延迟不再必然导致 `E_STALE_REF`、60 秒超时不再是安全参数、
以及**审批期间可以锁屏或切到别的 App**——而 D1「身份必须归属到活动 APPLICATION 窗口」
一个字都不放宽。

## 1. 今天的模型与它的四个后果

`SafetyGate.execute` 现在做的是：读一次上下文 → 人批准 → **再读一次** → 与第一次**逐字段相等**
（package / activity / 身份来源 / focusIdentity / focusedInputBounds / inputCommitEvidence /
preparedTargetEvidence）→ 执行。任何一项变了就是 `E_STALE_REF`，终态。

它挡住的东西是真实的：批准的那一刻与执行的那一刻必须是同一个现场。问题在于**它用实现细节来
表示"同一个现场"**，于是：

1. **人慢就会白批一次。** 焦点几何随键盘升降变、IME 会话随 InputConnection 重建变、自举身份
   会被随后的窗口事件升级成事件身份——这些都不改变"往谁发什么"，却都判 stale。
   代价已经如实记在 [通知栏审批布局 spec](2026-08-01-通知栏审批布局-design.md) §5.3。
2. **60 秒超时被迫兼任安全参数。** 它真正在保的是"证据别放太久"，可它写起来像"人得多快回应"。
   两件事挤在一个数字上，调哪边都不对。
3. **锁屏审批结构性走不通**（同篇 §5.4）：锁屏后前台身份不可知，危险动作在
   `requireKnownForeground` 就结束，**卡与通知都不会出现**。
4. **卡上给人看的东西越来越像给机器看的。** 8 项证据里真正参与人的判断的是三项：档位、
   目标会话、明文预览；其余五项人核对不了，也不该要求人核对
   （knowledge 已立条：**判据把实现细节当成了语义**）。

## 2. 上移之后：批准什么、执行前校验什么

### 2.1 意图（`ApprovalIntent`）

批准对象是一条**语义意图**，字段只放人能判断、且跨时间稳定的东西：

| 字段 | 例子 | 为什么在里面 |
|---|---|---|
| `riskTier` | 可撤回 / 不可逆 | 人第一眼要判"要不要立刻处理" |
| `actionKind` | 发送消息 / 点击「确认交易」 | 语义动作，不是 `press_key(enter)` |
| `targetPackage` | `com.tencent.mm` | 硬相等，不放宽 |
| `targetLabel` | 文件传输助手 | 人核对的那一行（来自 `preparedTargetEvidence.label`） |
| `contentSha256` / `contentLength` / `preview` | 明文预览 + 长度 + 摘要 | 内容锁死；预览是人看的，sha256 是机器比的 |
| `intentId` | 一次性 | 与 `confirmationId`/nonce 绑定，一次意图只授权一次执行 |
| `createdAtMs` | — | 意图自身的新鲜度（§2.4 第一个时钟） |

**不在里面**：windowId、activityName、focusIdentity、focusedInputBounds、身份来源、参数指纹。
它们不是不重要——它们在**执行那一刻**仍然被完整校验（§2.3），只是不再要求"与批准那一瞬相同"。

### 2.2 时序：为什么这样就绕开了锁屏那道墙，而且一个字没放宽

```
① 感知与准备   前台已知、证据齐全（今天就是这个要求，不变）→ 建立意图
② 弹卡 + 推通知  人可以走开、切 App、锁屏
③ 人作出决定    可以发生在锁屏上（只需要通知，不需要前台身份）
④ 等前台恢复    有界等待，直到前台重新是 intent.targetPackage（网关内部，不是大脑重试）
⑤ 重新感知      新的一次 contextProvider 读数
⑥ 完整严格链 + 意图匹配   任一不成立 → 终态失败，不重试
⑦ 执行
```

关键在①与⑦：**危险动作是在手机亮着、微信在前台、证据齐全时发起的**（agent 正在操作它），
锁屏发生在②～④之间。于是 `requireKnownForeground` **位置不用动、判据不用松**：调用发起时前台
本来就已知，执行前还要再要求一次。§5.4 那道墙拦的是"锁屏时才开始一次危险动作"，而这条路径
根本不做那件事。

**已知代价，如实写在前面**：人在锁屏上按下「允许」时，动作**不会当场发生**——它要等前台恢复。
对"发条消息"这类不紧急动作可以接受；对"确认交易"这类页面会消失的动作多半不可接受。

**用户 08-02 就此拍板：第④步只对 II 级开放**（§6 题四）。落到实现上是一句话——
**`foregroundWaitBudget` 按档位取值：II 级 300s（题五后），I 级 0**。I 级不进入等待，
批准与执行仍然紧挨着，只是判据同样换成§2.3 的意图匹配（**不保留两套判据并存**——
并存意味着两条路径要各自维护，其中一条迟早烂掉，而烂掉的那条恰恰会在最贵的时候被走到）。

**这句必须跟着一起读**：两档**仍然都逐次确认**，档位在这里决定的是"批准之后多久执行"，
**不是"要不要人点头"**。分级至今不产出任何免确认路径，这次也没有
（[风险分级 spec](2026-08-01-危险动作风险分级-design.md) §3.3 同一措辞）。

### 2.3 判据对照表——这张表是本篇的核心，改它等于改安全姿态

| 今天比什么 | 上移后比什么 | 强弱如实评估 |
|---|---|---|
| `packageName` 逐字段相等 | 与 `intent.targetPackage` 硬相等 | **不变** |
| `activityName` 相等 | **不比** | **更弱**。补偿：`targetLabel` 相等（会话名恰恰是人核对过的那一项）；且自举身份天生无 activity，今天这一项本来就时灵时不灵 |
| `identityBootstrapped` 相等 | **不比** | **更弱**。补偿同上；package 仍硬相等 |
| `focusIdentity` 相等 | 不跨时间比，改为**执行这一刻三处证据的身份互相一致**（今天的 `chainValid`，一字不动） | **侧移**：从"跨时间相等"变成"同一时刻自洽" |
| `focusedInputBounds` 相等 | 不跨时间比，`boundsConsistent(source, bounds)` 照旧 | 侧移，同上 |
| `inputCommitEvidence` 整体相等 | `sha256` + `length` 与意图相等，且证据必须**未过期** | **等价或更强**：人核对的就是内容 |
| `preparedTargetEvidence` 整体相等 | `label` + `packageName` 与意图相等，且未过期 | **等价** |
| 参数指纹相等 | 照旧（工具参数在批准后不许变） | 不变 |

两处"更弱"必须被看见，不许在实现时悄悄糊过去。它们换来的是：**人机延迟不再是安全事件**。

**用户 08-02 已拍板接受这两处**（§6 题三）。接受的理由记在这里备查：被替下来的两项本来就
时灵时不灵（自举身份天生没有 activity），而顶上去的 `targetLabel` 恰恰是人在卡上真正核对过
的那一项——**用人核对过的东西去承担判据，比用人核对不了的东西更结实。**
表里任何一行的松动都是安全姿态变更，**要改先回 B 道**。

### 2.4 三个时钟必须分开，且**它们被短时证据的 TTL 卡住**

| 时钟 | 保的是什么 | 今天 | **拍定值（08-02）** |
|---|---|---|---|
| `intentTtl` | "世界还是我批准时那个世界" | 无此概念 | **360s**（题五后改；不再等于证据 TTL） |
| `decisionTimeout` | 人多久没理这条审批 | 60s，且兼任了上面那件事 | **90s** |
| `foregroundWaitBudget` | 批准后等前台恢复多久 | 无此概念（今天当场判 stale） | **300s = 用户拍的那 5 分钟**（I 级为 **0**，见 §6 题四与 §6.1） |

**一条硬约束，会直接决定这三个数怎么取**：`InputCommitEvidence` 与 `PreparedTargetEvidence`
的 TTL 当前都是 **120 秒**（`DEFAULT_TTL_MS`）。也就是说**从建立意图到执行，总共只有两分钟**——
`decisionTimeout + foregroundWaitBudget` 一旦超过它，执行时的内容/目标证据必然已经过期，
链重建不起来，动作照样做不成。**"把超时调大"在今天这套证据下是句空话。**

出路有三条，**用户 08-02 选了 A**：

- **A（已拍定）** 三个时钟合计压在 120s 内：`decisionTimeout` 60→**90s** + `foregroundWaitBudget`
  **30s**，合计正好触到证据 TTL。收益有限但零新增风险——先拿到"人机延迟不再必然 stale"这一条。
- **B（已排除）** 把证据 TTL 一起调大。**这是往 fail-closed 松的那一侧动**，用户明确不动。
- **C（另立一项，不并进本篇）** 批准后允许网关**重建**证据：重新读一次会话面、重新提交同一段
  文本，并要求重建结果的 `sha256` 与意图相等。不放宽任何要求，但引入一个新形态——
  **批准之后网关自己动了一次手**。单独想清楚的清单见 §8 第 3 条。

> **2026-08-02 题五后 A 已被取代**：选项 C 落地后证据可以重建，"意图必须在原证据还活着时消费掉"这个耦合理由消失，有效期与等前台预算按用户拍的 5 分钟重取（§6.1）。**上面 A/B/C 保留备查**——它们记着当初为什么只能压在 120s 内，也解释了为什么必须先做 C。**当前生效的数以 §6.1 与 `IntentApprovalClocks` 为准。** 原文如下：A 的边界是 90 + 30 已经顶到 120s 天花板，所以"人走开五分钟再回来批准"当时做不到。
要突破它只有 C。**别把这个上限当成实现时可以微调的参数**——它由证据 TTL 推出来，
§5 第 4 条要求把这层关系写成断言而不是注释。

## 3. 与硬门不变量的关系

不变量 4 今天的措辞是「**一次确认只授权当前这一次调用，不生成可重放的通用令牌**」。

- **实质不变**：意图存在进程内存里、与 `confirmationId`/nonce 绑定、**一次消费**、不落盘、
  不进 MCP 信封 / trace / 审计 / 台账。大脑没有任何路径能拿到或重放它——与批次 2 那条红线
  （审批通道让大脑碰不到）同一套机制。
- **字面改写已由用户拍板（08-02，§6 题二）**。改写后的措辞，一字如下：

  > **一次确认只授权当前这一个意图的唯一一次执行，不生成可重放的通用令牌。
  > 意图不因执行失败而复活。**

  第二句与第一句同等重要，**必须写在同一处**：第一次执行尝试无论成功还是失败，意图立即作废；
  重来必须重新走一次人的批准。否则"有界等待 + 可重试"凑在一起，就长成了决定四那种
  **看起来有上限、其实是个重放口子**的东西。

- **改写在哪一刻生效**：跟着实现走。[硬门 spec](2026-07-19-危险动作统一硬门-design.md) §2 的
  现文**在语义意图落地之前仍然是准确的**（今天确实是"一次调用"），提前改会让它描述一个
  还不存在的机制——那是同一族坑的镜像。落地那次提交必须同时改到硬门 spec §2、
  `SafetyGate` 里 `RiskTier` 那段注释，以及本节。

## 4. 与站规的接缝（站规一字不改）

- **安全失败仍是终态。** §2.2 第⑥步任一不成立 → 常规失败，大脑不得重试、不得输出
  `[AWAIT_CONFIRM]`。上移只让 stale 变罕见，不改变它发生之后的处置。
- **第④步的有界等待是网关内部行为**，发生在一次工具调用**内部**，不是大脑再调一次。
  这正是决定四栽跟头的地方的反面：那条机制要靠大脑重试才能触发，而站规禁止重试，于是计数器
  连 1 都到不了（[通知栏审批布局 spec](2026-08-01-通知栏审批布局-design.md) §5.3）。本篇的等待
  不依赖大脑做任何事，**所以它是可达的**。
- 危险动作提示词与腿模板**不动**，黄金回归不受影响。

## 5. 落地切分（供排期，不在本篇拍板）

**A 道离线可验**（`scripts/check.ps1` 能给结论）：

1. `ApprovalIntent` 与 `IntentMatchPolicy.matches(intent, context)` —— 纯 Kotlin 纯函数，
   §2.3 那张表逐行一条用例，含**每一行的反例**（label 变了、sha256 变了、package 变了、证据过期）。
2. 意图的一次性与不可重放：`IntentApprovalStore` 单条、消费即销毁、执行失败也销毁。
3. `SafetyGate` 新路径的用例：④等待超时 → 终态失败且 `executor` 调用次数为 0；
   ⑥不匹配 → 终态失败且调用次数为 0（与既有 `confirmerCalls == 0` 同一形态的机械证据）。
4. 三个时钟的取值与 TTL 的关系断言：`decisionTimeout + foregroundWaitBudget <= 证据 TTL`
   题五之后是两条：`intentTtl >= foregroundWaitBudget`，以及**等前台预算一旦超过证据 TTL 就必须装配重建通道**（后者挂在 `IntentApproval` 上——那里能看见通道到底装没装，时钟只能拿一个可以写错的布尔当依据）。**写成断言而不是注释。**
5. **档位差异的两条用例**（§2.2 拍定）：I 级 `foregroundWaitBudget == 0`（不进等待）、
   II 级为 `DEFAULT_FOREGROUND_WAIT_BUDGET_MS`（题五后 = 300s，用常量不写死数字）；再加一条**回归断言**——**任一档位、未确认时 handler 调用次数仍为 0**，
   与风险分级 spec §6 第 4 条那条同形态。档位第一次有行为差异，那条断言就第一次真的在防事。

**已落地（2026-08-02，A 道，26 条离线用例）**：`ApprovalIntent` / `IntentMatchPolicy` /
`IntentApprovalStore` / `IntentApprovalClocks`（构造即断言）/ `SafetyGate.resolveViaIntent`，
外加把 Enter 证据链抽成 `EnterChainPolicy` 供两处共用（**判据有两份，迟早只改一份**）。
做过一次**正对照**：把 `targetLabel` 那行判据短路成永真，`ApprovalIntentTest` 与
`SafetyGateIntentPathTest` 各红一条，还原后全绿——判据确实接在它要判的那条路径上。

**默认关着**：`SafetyGate(intentApproval = null)` 就是今天的行为，生产装配未改。
打开它属于安全姿态变更，进 C 道批次。

**C 道真机**：一条新腿（批准后切走再回来），验④⑤⑥真的按顺序发生；以及锁屏批准 → 解锁回微信
→ 动作完成这条完整链路。**打开开关与这条腿是同一个批次的事**，不得分开：开关一开，
三腿走的就是新判据。

### 6.1 新的一道 B 道题（2026-08-02 选项 C 落地后冒出来，**一个数都还没改**）

**题五 · 意图有效期取多长？**

题一当初选 A（压在 120s 证据 TTL 内）**成立的理由是"意图必须在原证据还活着的时候消费掉"**。
选项 C 落地后**证据可以重建**，这个耦合理由就没了——于是 90s 决定期够不够，变成一个
**独立的、必须重新回答的问题**：用户要的场景是"批准完去干别的、回头动作已经做好"，
而"干别的"很容易超过 90 秒。

| 选项 | 意图有效期 | 换来什么 | 代价（如实写） |
|---|---|---|---|
| **A** | 维持 90s + 30s | 零新增风险，与今天一致 | "走开几分钟再回来"仍然做不到——**选项 C 的收益只兑现一半** |
| **B** | 3～5 分钟 | 覆盖"接个电话/看一眼别的 App 再回来" | 人可能已经忘了自己批过什么；一条几分钟前的批准仍能生效 |
| **C** | 10 分钟以上 | 覆盖"放下手机去做别的事" | 同上且更重：**批准与执行之间的世界变化越多，"同一个现场"越名不副实**；同名会话这类既有风险的窗口被同比例拉长 |
| **D** | 不设固定值，按档位分：II 级放宽、I 级维持 90s | 与题四同一逻辑——不可逆的那档不该等 | 多一处档位差异，实现与验收都更复杂 |

**几条判断依据，供拍板时用**：

- **有效期与"证据新鲜度"已经解耦**，所以放宽它**不再**意味着"拿一条十分钟前的输入证据去发送"
  ——执行前会重读、重建、与卡上那份比对。放宽的是**人的记忆窗口**，不是证据窗口。
- **真正被拉长的风险是"人忘了"**：批准后十分钟，用户未必记得自己批过什么，而动作仍会发生。
  这是**人因风险**，不是机械风险，只有用户本人能判断自己能接受多久。
- **锁屏那条链需要多长，取决于用户的实际习惯**（解锁回微信通常几秒还是几分钟）。
- 通知本身的存活时长跟着决定期走（`setTimeoutAfter`），所以有效期也决定了"那条审批通知在
  通知栏里挂多久"。

**在拍板之前，代码里一个时钟都不动**：`IntentApprovalClocks` 仍是 90 + 30，构造断言仍在。

**四条决定里没有任何一条放宽了"要不要确认"。** 两档仍然都逐次确认，分级仍然不产出任何免确认
路径；§2.3 那张表里没有一行是"少比一项"，两处更弱都由人核对过的语义项顶上。
**把这四条读成"硬门开始松了"是错的。**

## 7. 非目标

- **不做任务级额度、不做免确认路径。** 一次意图仍然只授权一次执行。
- **不放宽 `requireKnownForeground`、不给 keyguard 开特例**（§2.2 说明了为什么不需要）。
- **不做跨设备批准**（推到 PC 或另一台手机）。红线"审批通道让大脑碰不到"在跨设备下需要一套
  独立通道与独立凭据，与本篇正交；重开条件：本篇落地且本机通道稳定之后单独立项。
- 不改感知面、工具面、站规、腿模板、确认卡现有 8 项证据的内容与顺序。

## 8. 未决与风险

0. **【已解除】** 下面这条边界由**选项 C（批准后重建证据）**解除——用户 2026-08-02 拍板
   「先做选项 C，一次交付走开也能用」，实现与判据已落地（`EvidenceRebuildPolicy` +
   `SafetyGate` 里那段**只在证据真的没了时才走**的恢复步骤）。**保留原文备查**，因为它解释了
   为什么必须做选项 C，也解释了重建的锚点为什么只能是语义而不能是 IME 身份：

0. **本方案的收益边界，比 §2.2 写的窄（2026-08-02 离线读码补记，写验收单时才发现）**：
   「批准后延后执行」只覆盖**人慢但没离开输入会话**，**不覆盖"切走再回来"**。
   机制：输入证据按**焦点身份**取（`InputCommitEvidenceStore.current` 身份不等即视为无证据），
   而 IME 会话 id **每次 `onStartInput` 重新生成**（自增 generation 参与哈希）。切走再回来
   必然重新 `onStartInput` → 新身份 → 旧输入证据取不出来 → 意图匹配在"没有短时输入提交证据"
   上失败。**这不是判据太严，是证据本身已经不在了。**

   直接后果两条：①§2.2 时序图里"锁屏批准 → 解锁回微信 → 动作完成"这条**当前走不通**；
   ②§5 那条 C 道新腿在选项 C 落地前**预期失败**，不许当成待修缺陷。
   **要覆盖它只有 §2.4 选项 C（批准后重建证据）**——它从"下一步单独立项"变成了
   **"想要那半收益就必须做"**，优先级应重估。这条改变了本篇的价值判断，需回 B 道。

1. **同名会话**（微信分身、同名群）：`targetLabel` 相等挡不住。这是**既有风险**，今天也只比
   label，本篇不新增也不解决；真要解决需要会话级稳定标识，属另一篇。
2. **等待期间目标 App 被杀/重启**：前台恢复了但会话面不是原来那个，证据链会自己判失败
   （fail-closed 方向正确），但用户体验是"白批一次"。有界等待的失败措辞要说清楚发生了什么。
3. **重建证据（题一 C）已定为下一步单独立项**，起点问题记在这里：重建本身是一次 UI 变更，与
   `UiMutationCoordinator` 的既有失效规则怎么接、被重建覆盖掉的用户手动输入怎么办。
4. 本篇所有结论来自离线读码，**没有一条经过真机**。§5 的 C 道那条腿是它的第一次真机验证。

## 9. 生产装配实施笔记（2026-08-02，**动装配之前先读完这一节**）

写这一节的理由很实际：**装配是这批唯一真正改变真机行为的一步**（开关一开，既有三腿全部改走
新判据），而它需要的前提此前只散在几轮会话里。**带着残缺的前提做装配，错会一路带到真机，
而真机那一轮花的是用户的时间。**

### 9.1 四处装配点，各传什么、为什么

| # | 位置 | 传什么 | 为什么是这个值 |
|---|---|---|---|
| 1 | `ToolRegistry.newSafetyGate` | `intentApproval = IntentApproval(...)` | **开关本身**。不传就是今天的行为 |
| 1a | ↳ `intentIdFactory` | `ConfirmationIdGenerator.next()` | 与 confirmationId 同源、一次性；不落盘、不进信封 |
| 1b | ↳ `awaitForeground` | 轮询 `a11y.ctx()` 直到 `foreground_known && app == 目标包`，间隔 ≤200ms，用完预算返回 false | 这段等待发生在**一次工具调用内部**，不是大脑重试——站规「安全失败即终态」一字未动 |
| 1c | ↳ `rebuildEvidence` | 见 §9.2 | 预算 300s > 证据 TTL 120s，**不装它 `IntentApproval` 构造直接抛** |
| 2 | `ConfirmOverlay.ask` | `timeoutMs = clocks.decisionTimeoutMs`（90s） | 卡的默认 60s **比决定预算还短，本来就自相矛盾**；通知跟着 `setTimeoutAfter(timeout + 15s)` 一并放宽到 105s |

**runner 两个超时：实测算式如下，结论是两个都不用改**（这与最初的估计不同，如实记）：

- `-ConfirmationTimeoutSec` 当前默认 **120s** ≥ 卡的新超时 90s ✓。**不改。**
  （它必须 ≥ 卡超时，否则 runner 先超时、人还在核对，会得出"人没决定"的错误结论。）
- `-DispatchTimeoutMin` 当前默认 **15 分钟 = 900s**。新腿最坏耗时 ≈ 决定 90s + 等前台 300s +
  宏与输入开销 ~120s ≈ **510s** ✓。**不改。**
- 顺带核过第三个：debug 测试控制的 `expires_at_ms = min(300, ConfirmationTimeoutSec + 60) = 180s`。
  它只在 `afterAllowed`（**等前台之前**）被检查，覆盖得住 90s 决定期 ✓。**不改。**

**若装配时发现还得动第四个数，停下来问主会话**——用户拍的是"5 分钟回来还算数"这个行为，
不是某一个具体常量。

### 9.2 两处证据重建：各读什么、走哪条腿

| 重建对象 | 读什么 | 通道 | 基线 |
|---|---|---|---|
| 输入证据 | 输入框当前文本 | **微信只有 OCR 这条腿**（a11y 树被屏蔽） | `intent.contentSha256` / `contentLength`——**卡上给人看过的那份** |
| 目标会话证据 | 会话页顶部标题 | 同上；用宏那条 `isConversationSurface` 的**同一个信号**，不另起一套 | `intent.targetLabel` + `targetPackage` |

判定走 `EvidenceRebuildPolicy.judge(intent, readback, channel, surfaceLabel)`，**先验会话、再验内容**。
装配方只负责"读"与"读到之后把证据按当前身份重新落进证据仓"，**判定不许在装配方另写一份**。

三态落到 `safety_code`：

| 结论 | `safety_code` | 含义 |
|---|---|---|
| `Rebuilt` | 继续走意图匹配，最终 `OK` | 现在框里/页上的东西与卡上那份一致 |
| `Mismatch` | `E_STALE_REF` | 读到了，但内容或会话在人批准之后变了——**正确拦截** |
| `Unverified` | `E_VERIFY_FAIL` | 读不回来（OCR 一个字没出、通道不可用、未装配） |

### 9.3 现场判据：OCR 抖动 → `E_VERIFY_FAIL` 是**正确的 fail-closed**，不是"新功能不稳定"

两处重建读的东西**在微信上都只有 OCR 那条腿**，所以新腿在 OCR 抖动下会**偶发**以
`E_VERIFY_FAIL` 终态。**这条必须写进验收单**：第一次撞上时，如果没人事先说清楚，现场几乎
必然把它读成"这功能不行"——**而结论方向正好反了**：它说明"判不了就不放行"这条在起作用。

判别方法（现场按这个分）：

- `E_VERIFY_FAIL` + 原因含「读不回来 / 为空」 → **取证链抖动**，重跑即可，不改任何判据。
- `E_STALE_REF` + 原因含「与已批准的不符」 → **内容或会话真的变了**，那是拦对了，查为什么变。
- 连续多轮都是 `E_VERIFY_FAIL` → 才是"OCR 这条腿在这一步不够用"的信号，那时再谈方案。

### 9.4 开关打开后三腿各自的变化（验收单 §3.3 的依据）

- **Allow**：语义未变 → 照常放行。焦点身份与几何**允许变**，不再参与比较。证据没丢 →
  **重建一步都不走**（有离线用例钉 `rebuildCalls == 0`）。
- **Stale**：仍 `E_STALE_REF`，但**理由变成"等前台恢复超时"**。生产预算是 5 分钟，而这条腿
  按定义永不把微信切回来，所以**监督式跑测经 debug 测试控制给它一个短预算**
  （`IntentApprovalClocks.withShorterForegroundWait`，建议 20s）。
  **该接口只许缩短、不许延长**——延长会让用户拍板的行为被测试脚手架悄悄改掉；缩短只会更早
  终态，方向上 fail-closed，不对称由离线用例钉住。
  **现场看到它几十秒内终态是对的；等满 5 分钟说明短预算没生效，报回来。**
- **Deny**：拒绝发生在意图创建**之前**，这条路径一个字没变。
- **新腿**（批准后切走再回来）：靠 §9.2 那两处重建成立，是这批唯一的新增收益。

### 9.5 ⚠️ 装配前发现的判据缺口：**OCR 通道上 sha256 相等是不可能满足的**

**动装配时按 §9.2 去接第一条读回通道，当场撞上的**：`EvidenceRebuildPolicy` 现在用
`sha256(readback) == intent.contentSha256`——**逐位相等**。而微信这条链只有 OCR，
OCR 读回的从来不是逐位相同的串（大小写、空白、形近字；本仓实测「低对比度短文本漏识近四成」，
marker 字母表 `3479AHKMPTXY` 与 O→0 归一就是为此存在的）。

后果不是"偶尔失败"，而是**方向错误的失败**：读回来的串与批准的不逐位相同 → 判 `Mismatch`
→ 台账上写着「内容在人批准之后被改过」。**那是对用户的诬告**，而且正是我自己在同一个文件里
警告过的形态——只不过我把它防在了"空串"上，没防在"OCR 本来就不逐位相同"上。

**既有代码早就知道该怎么比**：`UiTools.ocrReadbackWithRetry` 用的是
`OcrEngine.norm(got).contains(OcrEngine.norm(expected))`——**归一后包含**，不是相等。
判据要与通道的物理特性相称，这条本仓已经付过学费。

**但换成"归一后包含"需要一样现在没有的东西：被批准内容的明文**。意图里只有 `sha256` 与
`length`，**sha256 不可逆**，拿它没法做包含比较。三条出路，各自的代价：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A** | 意图里带上**归一后的明文**（或 ≤64 字的 `preview`），OCR 通道按归一包含比，a11y 通道仍按 sha256 相等比 | 明文多存在一处进程内存（**卡上本来就展示过它**，不落盘、不进信封）；`preview` 截断意味着 **>64 字的内容只能验前 64 字** |
| **B** | 重建只认 a11y 通道，OCR-only 的 App 一律 `Unverified` | 微信恰恰是 OCR-only ——**等于 5 分钟收益在唯一的目标 App 上永远兑现不了** |
| **C** | 两条都要：a11y 能读就按 sha256，读不到才退 OCR 归一包含，并在结论里标明用了哪条 | 最贴近既有 `IdentitySource.A11Y / IME_ONLY` 的两档形态，但实现与用例都翻倍 |

**倾向 C**（与既有降级链同构，且"用了哪条通道"本来就要进 `safety_code` 的原因串），
**但这决定了"重建到底能保证什么"**——A 的截断、B 的不可用，都是用户能感知的行为差异，
所以按老规矩交回 B 道，**在拍板前不动判据**。

**顺带记一条方法论**：这个缺口不是写代码时冒出来的，是**去接第一条真实通道时冒出来的**。
§9 那份实施笔记写得再全，也只覆盖到"我已经想到的接线"；**判据与物理通道相不相称，
要等真的去接才暴露**。下次写这类笔记时，应当把"每条判据对应的通道能不能物理满足它"
显式列成一栏。
