# 设计说明：把审批对象从「证据快照」上移到「语义意图」

## 0. 一句话结论

**人批准的是「往文件传输助手发这条消息」，不是批准那一瞬的 windowId、bounds、IME 会话 id。**
审批对象上移到语义意图后，执行前校验**一条都不减**：重新感知、重新走完整严格链，拿新证据去比**意图**。

由此：人机延迟不再必然导致 `E_STALE_REF`；60 秒超时不再兼任安全参数；审批请求挂起期间可以锁屏或
切到别的 App，返回可见确认卡后再批准——而 D1「身份必须归属到活动 APPLICATION 窗口」一个字都不放宽。

## 1. 现行模型的问题

`SafetyGate.execute` 现在是：读一次上下文 → 人批准 → 再读一次 → 与第一次**逐字段相等**
（package / activity / 身份来源 / focusIdentity / focusedInputBounds / inputCommitEvidence /
preparedTargetEvidence）→ 执行；任一项变了就是 `E_STALE_REF`，终态。它用实现细节表示"同一个现场"，于是：

1. **人慢就白批一次**：焦点几何、IME 会话、自举身份升级都会判 stale，却不改变"往谁发什么"
   （代价见[通知栏审批布局 spec](2026-08-01-通知栏审批布局-design.md) §5.3）。
2. **60 秒超时被迫兼任安全参数**：它真正保的是"证据别放太久"。
3. **锁屏时新发起危险动作结构性走不通**（同篇 §5.4）：在 `requireKnownForeground` 就结束，
   卡与通知都不会出现。这不能读成允许在锁屏通知上批准。
4. **8 项证据里人真正能核对的只有三项**：档位、目标会话、明文预览。

## 2. 上移之后：批准什么、执行前校验什么

### 2.1 意图（`ApprovalIntent`）

批准对象是一条**语义意图**，字段只放人能判断、且跨时间稳定的东西：

| 字段 | 例子 | 为什么在里面 |
|---|---|---|
| `riskTier` | 可撤回 / 不可逆 | 人第一眼要判"要不要立刻处理" |
| `actionKind` | 发送消息 / 点击「确认交易」 | 语义动作，不是 `press_key(enter)` |
| `targetPackage` | `com.tencent.mm` | 硬相等，不放宽 |
| `targetLabel` | 文件传输助手 | 人核对的那一行（来自 `preparedTargetEvidence.label`） |
| `contentSha256` / `contentLength` / `preview` | 明文预览 + 长度 + 摘要 | 内容锁死；预览是人看的，sha256 是机器比的 |
| `intentId` | 一次性 | 与 `confirmationId`/nonce 绑定，一次意图只授权一次执行 |
| `createdAtMs` | — | 审批请求建立时刻，只用于 `decisionTimeout` |
| `approvedAtMs` | 初始为空 | 仅在真人「允许」胜出时原子写入一次；从这里起算 `intentTtl`，写入后不可刷新 |

**不在里面**：windowId、activityName、focusIdentity、focusedInputBounds、身份来源、参数指纹。
它们在**执行那一刻**仍被完整校验（§2.3），只是不再要求"与批准那一瞬相同"。

### 2.2 时序：挂起请求与前台恢复，不恢复锁屏通知批准

```
① 感知与准备   前台已知、证据齐全（现行要求不变）→ 建立意图
② 绘制可见卡 + 推通知   通知只提供拒绝和查看证据；人可暂离、切 App 或锁屏
③ 人作出决定    只能在完成绘制与取证门的可见 ConfirmOverlay 点击允许；允许胜出时一次性写 approvedAtMs
④ 等前台恢复    仅 II 级有界等待，直到前台重新是 intent.targetPackage（网关内部，不是大脑重试）
⑤ 重新感知      新的一次 contextProvider 读数
⑥ 完整严格链 + 意图匹配   任一不成立 → 终态失败，不重试
⑦ 执行
```

危险动作在前台已知、证据齐全时发起；锁屏只能发生在请求建立之后，锁屏期间不能批准，须返回可见确认卡
并在 `decisionTimeout` 内作决定。`requireKnownForeground` **位置不动、判据不松**：发起时前台已知，
执行前再要求一次。§5.4 那道墙拦的是"锁屏时才开始一次危险动作"，这条路径不做那件事。

**已知代价**：通知不能批准；人在确认卡上批准后切走或锁屏，II 级动作要等前台恢复并重新校验证据才发生。

**用户 08-02 拍板：第④步只对 II 级开放**（§6 题四；08-03 只修订等待时长）。
`foregroundWaitBudget` 按档位取值：**II 级 300s，I 级 0**。I 级不进入等待，批准与执行仍紧挨着，
判据同样换成 §2.3 的意图匹配，**不保留两套判据并存**。

**两档仍然都逐次确认**，档位决定的是"批准之后多久执行"，不是"要不要人点头"；分级不产出任何免确认路径
（[风险分级 spec](2026-08-01-危险动作风险分级-design.md) §3.3 同一措辞）。

### 2.3 判据对照表——改它等于改安全姿态

| 今天比什么 | 上移后比什么 | 强弱如实评估 |
|---|---|---|
| `packageName` 逐字段相等 | 与 `intent.targetPackage` 硬相等 | **不变** |
| `activityName` 相等 | **不比** | **更弱**。补偿：`targetLabel` 相等（会话名恰恰是人核对过的那一项）；自举身份天生无 activity |
| `identityBootstrapped` 相等 | **不比** | **更弱**。补偿同上；package 仍硬相等 |
| `focusIdentity` 相等 | 不跨时间比，改为**执行这一刻三处证据的身份互相一致**（`chainValid`，一字不动） | **侧移**：从"跨时间相等"变成"同一时刻自洽" |
| `focusedInputBounds` 相等 | 不跨时间比，`boundsConsistent(source, bounds)` 照旧 | 侧移，同上 |
| `inputCommitEvidence` 整体相等 | `sha256` + `length` 与意图相等，且证据必须**未过期** | **等价或更强** |
| `preparedTargetEvidence` 整体相等 | `label` + `packageName` 与意图相等，且未过期（适用范围见 §2.5） | **等价** |
| 参数指纹相等 | 照旧（工具参数在批准后不许变） | 不变 |

两处"更弱"**用户 08-02 已拍板接受**（§6 题三），实现时不许悄悄糊过去：被替下来的两项本来就时灵时不灵，
顶上去的 `targetLabel` 是人在卡上真正核对过的那一项。
表里任何一行的松动都是安全姿态变更，**须先说明取舍并取得用户真实决定、记录来源后才能改**。

### 2.4 三个时钟必须分开，证据 TTL 也不能冒充意图有效期

| 时钟 | 保的是什么 | **现行值（08-03，覆盖 08-02 题一）** |
|---|---|---|
| `decisionTimeout` | 人多久没理这条审批 | 从 `createdAtMs` 起 **90s** |
| `intentTtl` | 真人允许后，这个一次性意图还允许被执行多久 | 从 `approvedAtMs` 起 **360s** |
| `foregroundWaitBudget` | 批准后等前台恢复多久 | II 级 **300s**；I 级 **0**（§6 题四） |

`InputCommitEvidence` 与 `PreparedTargetEvidence` 的 TTL 仍为 **120 秒**（`DEFAULT_TTL_MS`），
**不随意图有效期放宽**。等待越过 120s 后旧证据不能直接用于执行；长等待路径必须实际装配**证据重建通道**：
重新读取会话与输入内容，重建两处证据，并与确认卡上人核对过的目标/内容摘要逐项比对。
`Mismatch` 或 `Unverified` 一律 fail closed，只有完整的 `Rebuilt` 才能继续。

决定沿革：08-02 先选 90s 决策 + 30s 等待；08-03 为满足"批准后最多隔五分钟回到微信"改为上表数值，
同时把重建通道升级为长等待路径的硬前置。放宽证据 TTL 被明确排除。

两个起点不能混：批准前只有 90s 决策时限，没有可执行有效期；只有真人「允许」胜出时才原子写入一次
`approvedAtMs` 并启动 360s。批准时间不可刷新，拒绝、超时、失败或重复回调都不能创建或延长它；
意图一次消费、失败不复活。300s 前台等待之后余下 60s 留给重建、严格比对与执行。

实现必须把三条关系写成机械断言，而不是注释：

1. `approvedAtMs` 只能由胜出的真人允许写入一次且不可刷新，并满足 `intentTtl >= foregroundWaitBudget`；
2. 任一路径只要可能等到证据 TTL 之外，就必须在**看得到真实通道是否装配**的位置断言重建通道在位，
   不得用一个可被写错的布尔值代替；
3. 执行前必须重读目标与内容，并与确认卡摘要比对。放宽的是可等待时长，不是内容完整性。

### 2.5 `preparedTargetEvidence` 按档位收窄（用户 2026-09-02 拍板）

全仓只有 P0 准备宏记录 `preparedTargetEvidence`；若意图路径无条件要求它，非宏的危险 `ui_action`
会一律 `E_STALE_REF`，以"这条路径没人走"的形态藏着。实际受影响的只有命中 `send_words` 的 II 级点击
（`ui_action` 未命中风险词按 fail-closed 归 I 级）。

**拍板：按档位收窄。**

| 动作类 | 要不要 `preparedTargetEvidence` | 依据 |
|---|---|---|
| `press_key(enter)` / `type_text` | **要**，照 §2.3 表 | 送进会话，证据语义成立 |
| **II 级** `ui_action`（命中 `send_words`，如点「发送」） | **要**；须为它补一个非宏的目标会话证据产出点 | 这类点击按定义发生在会话里 |
| **I 级** `ui_action`（其余，含未命中词表） | **不要**，沿用逐字段相等（`ref`/`text`/`description`/`bounds`/`source`）+ 每次必确认 | 不进延后执行路径，无跨时间窗口需要弥合 |

`PreparedTargetEvidence` 的语义是"正要送进哪个会话"；要求无会话动作提供它，只会逼出合成会话，
把"人核对过的那一行"变成"系统编出来的那一行"。

**这条不放宽任何已有判据**：I 级本来就要求确认与执行紧挨着，逐字段相等是它已有的门；II 级新增证据
产出点是补强。II 级 `ui_action` 的证据产出点必须与 P0 宏同源同规则（含 TTL 与重建三态），不得另起弱化版本。

## 3. 与硬门不变量的关系

不变量 4 现行措辞：「**一次确认只授权当前这一次调用，不生成可重放的通用令牌**」。

- **实质不变**：意图存在进程内存、与 `confirmationId`/nonce 绑定、**一次消费**、不落盘、
  不进 MCP 信封 / trace / 审计 / 台账；大脑没有任何路径能拿到或重放它（与审批通道红线同一套机制）。
- **字面改写已由用户拍板（08-02，§6 题二）**，改写后措辞：

  > **一次确认只授权当前这一个意图的唯一一次执行，不生成可重放的通用令牌。
  > 意图不因执行失败而复活。**

  两句必须写在同一处：第一次执行尝试无论成败，意图立即作废，重来必须重新批准。
- **生效时机跟着实现走**：[硬门 spec](2026-07-19-危险动作统一硬门-design.md) §2 现文在生产接线前仍准确，
  不提前改；落地那次提交须同时改硬门 spec §2、`SafetyGate` 里 `RiskTier` 那段注释与本节。

## 4. 与站规的接缝（站规一字不改）

- **安全失败仍是终态。** §2.2 第⑥步任一不成立 → 常规失败，大脑不得重试、不得输出 `[AWAIT_CONFIRM]`。
- **第④步的有界等待是网关内部行为**，发生在一次工具调用内部，不依赖大脑重试，所以可达；
  这与已作废的限次重弹相反（[通知栏审批布局 spec](2026-08-01-通知栏审批布局-design.md) §5.3）。
- 危险动作提示词与腿模板**不动**，黄金回归不受影响。

## 5. 落地切分与进度

**离线可验**（`scripts/check.ps1` 能给结论）：

1. **✅ 已落地（2026-09-05）**：`ApprovalIntent` 与 `IntentMatchPolicy.matches(intent, context)`，
   `core/ApprovalIntent.kt` + `ApprovalIntentMatchTest`。覆盖 §2.3 逐行正反例（含刻意不比的三行，
   其正确行为是变了仍然匹配）、§2.5 按档位收窄、三个时钟分开（未获批不算存活、`intentTtl` 从
   `approvedAtMs` 起算、意图存活与证据匹配分开）。`isIntentLive` 与 `matches` **刻意分开**。
2. 意图的一次性与不可重放：`IntentApprovalStore` 单条、消费即销毁、执行失败也销毁；未允许时
   `approvedAtMs == null`，真人允许胜出后只写一次，重复回调、拒绝、超时与失败都不能设置或刷新它。
3. `SafetyGate` 新路径的用例：④等待超时 → 终态失败且 `executor` 调用次数为 0；
   ⑥不匹配 → 终态失败且调用次数为 0。
4. 三个时钟与重建通道的关系断言：`intentTtl >= foregroundWaitBudget`；等待可能越过证据 TTL 时，
   在能看见实际依赖装配的位置断言重建通道在位；执行前重读结果必须与确认卡摘要相等。**写成断言而不是注释。**
5. **档位差异用例**：I 级 `foregroundWaitBudget == 0`、II 级为 300s；回归断言——**任一档位、未确认时
   handler 调用次数仍为 0**（与风险分级 spec §6 第 4 条同形态）。

**2026-09-07 进度**：第 2、4 项的独立模块与第 5 项的档位等待预算用例已完成（新增 57 个 JVM 用例）。
`IntentApprovalStore` 每次确认一个实例，无 reopen/reset；消费先移除记录。
`IntentApprovalTiming`/`IntentApprovalDependencies` 在构造时检查三时钟关系和实际 reader 依赖，不使用可自报的布尔值。
`EvidenceRebuildPolicy` 已覆盖精确 a11y 与 **OCR 归一包含 / 4 字守卫**；标题归一后必须精确，保留 AO/A0 区分。
`IntentOcrBaseline.fromContent` 从同一份全文同时派生摘要、长度与归一文本，私有构造且不可拆改；
不保留原文，诊断文本脱敏。`OcrEngine.norm` 等价转发到共享 `TextNorm`。
时间逆序、非正 TTL、减法溢出、读回异常和 OCR 漏识均拒绝授权或返回不可验证。

**生产接线未完成**：第 3 项与第 5 项 handler 调用次数要随真实 `SafetyGate` 新路径一起验证；
审批来源、Android 证据安装与严格执行链尚未接入。生产接线时**只接受可见 `ConfirmOverlay` 的内部允许回调**，
通知 `allowed=true` 必须 fail closed；`Rebuilt` 只说明读回相符，不构成执行授权；I 级 `ui_action`
不调用会话读回，不要求合成会话。真机验收队列未清时按 [backlog](../backlog.md) 保持这些模块未接线，
不把基础模块单测升级为锁屏等待、回前台执行或真机行为通过。

**真机验收**：先在完成绘制与取证门的可见 `ConfirmOverlay` 批准，再切走或锁屏、返回目标 App，
验④⑤⑥按顺序发生；另验通知"允许"广播不能批准、锁屏期间不能从通知批准，拒绝和超时均不执行。
08-02 设想的"锁屏通知批准 → 解锁回微信 → 动作完成"是已撤销的历史方案，不是验收项。

## 6. 四条决定（用户 2026-08-02 拍板；题一由 08-03 后续决定覆盖）

| # | 题 | 决定 | 落点 |
|---|---|---|---|
| 一 | 意图有效期怎么取 | **08-03 最终值**：`intentTtl=360s`、`decisionTimeout=90s`；I 级 wait 0、II 级 `foregroundWaitBudget=300s`。证据 TTL 仍为 120s；长等待必须装配重建通道 | §2.4 |
| 二 | 硬门不变量 4 的措辞 | **同意改写**，并在同一处写明「意图不因执行失败而复活」 | §3 |
| 三 | §2.3 那两处如实标注的"更弱" | **接受** | §2.3 |
| 四 | I 级要不要也延后执行 | **只有 II 级走延后执行**，I 级批准与执行仍紧挨着 | §2.2、§5 第 5 条 |

被否或被替代的选项：

- **题一 B（调大证据 TTL）明确排除**——那是往 fail-closed 松的一侧动。
- **题一 C（批准后重建证据）被 08-03 采用**：五分钟等待只在重建两处证据、执行前重读并与确认卡摘要相等时成立，
  不拉长 120s 证据 TTL，不减少任何执行前校验。
- **题四 B（两档一样）被否**；[风险分级 spec](2026-08-01-危险动作风险分级-design.md) §3.3 已同步。

**四条决定里没有任何一条放宽了"要不要确认"。** 两档仍然都逐次确认，分级不产出任何免确认路径；
§2.3 表里没有一行是"少比一项"，两处更弱都由人核对过的语义项顶上。

## 7. 非目标

- **不做任务级额度、不做免确认路径。** 一次意图仍然只授权一次执行。
- **不放宽 `requireKnownForeground`、不给 keyguard 开特例**（§2.2）。
- **不做跨设备批准**（推到 PC 或另一台手机）：需要独立通道与独立凭据才能满足审批通道红线；
  重开条件：本篇落地且本机通道稳定之后单独立项。
- 不改感知面、工具面、站规、腿模板、确认卡现有 8 项证据的内容与顺序。
