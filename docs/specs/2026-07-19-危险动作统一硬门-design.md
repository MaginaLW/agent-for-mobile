# 设计说明：危险动作统一硬门

- 日期：2026-07-19（设计批准并离线实现）
- 范围：M1 执行网关 P0 安全修复
- 当前状态与真机验收进度见 [STATUS.md](../../STATUS.md) 与 [P0 规程](../runbooks/P0-safety-hard-gate-smoke.md)

## 1. 问题与根因

项目铁律要求发送、支付、删除类操作永远在临界动作前停下，人工确认后才能继续。修复前网关没有统一执行这条约束：

1. `ToolSpec.level` 只描述工具风险，`ToolRegistry.call()` 调用 handler 前不检查 `Level.D`。
2. `ui_action(click/long_click)` 仅在自身实现里按危险词触发悬浮窗，其他执行通道不经过这段逻辑。
3. `press_key(enter)` 被登记为普通写操作，却可能在聊天输入框中直接发送。
4. 独立 `confirm(action_desc)` 只返回布尔值，没有把批准绑定到具体工具、参数和当前页面，不能构成后续动作的机械授权。
5. `safety.json` 的“文件传输助手”发送白名单与项目铁律冲突。以铁律为准：所有发送动作都确认，不保留执行器侧免确认例外。

根因是风险等级、动态风险识别、确认 UI 和实际 handler 分散在不同层，缺少一个所有工具都绕不过的执行门。

## 2. 安全不变量

必须始终成立：

1. 所有 `Level.D` 工具在 handler 执行前都经过统一确认。
2. `Level.W` 工具可按参数和目标动态升级为危险动作；首批覆盖 `press_key(enter)` 与 `ui_action` 的发送/支付/删除目标。
3. 未确认、拒绝、超时、确认后上下文失效时，handler 调用次数必须为 0。
4. 一次确认只授权当前这一次调用，不生成可重放的通用令牌。
5. 确认卡片展示由网关生成的实际工具、关键参数、前台 App/Activity 和目标控件证据，不能只展示模型自由填写的描述。
6. 确认返回后重新校验前台 App/Activity；带 `ref` 的 UI 动作还要重新解析目标并核对文本、描述和 bounds。目标变化即返回 `E_STALE_REF`，不得执行。
7. 危险动作的请求、确认结果、上下文校验和最终结果全部写入审计；安全审计字段只记录判定结果、参数指纹和必要目标证据，不额外复制消息正文等敏感参数。
8. 安全失败不得进入重试守卫的“同法失败次数”，避免用户拒绝或等待确认被误判为执行故障。

## 3. 方案选择

- **方案 A：统一路由内联确认并执行（采用）**：`ToolRegistry.call()` 在 handler 前计算风险；危险调用阻塞等待 `ConfirmOverlay`，用户允许且上下文复核通过后，同一次调用立即执行 handler。授权天然绑定当前工具和参数；无令牌、缓存或重放面；对未来 D 工具自动生效。代价是工具调用会等待人工操作。
- **方案 B：显式一次性授权令牌（拒绝）**：先调结构化 `confirm(tool, args)` 获得短时令牌再交给危险工具。需要令牌存储、参数规范化、过期/消费/重放防护并修改所有危险工具 schema，P0 引入的状态面过大。
- **方案 C：逐工具补确认（拒绝）**：只给 `press_key(enter)` 加悬浮窗，无法保证未来 D 工具和其他通道不漏接，不解决根因。

## 4. 组件设计

### 4.1 `SafetyPolicy`：纯判定层

纯 Kotlin 判定组件，`Level` 下沉到 `core`。输入为工具名、静态等级、冻结参数和动态目标证据，输出 `Allowed` / `ConfirmationRequired(actionSummary, evidence)` / `Blocked(code, reason)`。

首批规则：

- `Level.D`：始终 `ConfirmationRequired`。
- `press_key(key=enter)`：始终按“可能发送/提交当前输入内容”确认；其他按键保持原等级。
- `ui_action(click|long_click)`：目标命中发送、支付、删除、账号/安装等词表时确认；发送词不因“文件传输助手”上下文免确认。
- 敏感 App 黑名单先于确认执行，人工确认不能绕过银行/证券默认拒进。

### 4.2 `SafetyGate`：统一执行门

调用顺序：

1. 校验工具存在、敏感 App 黑名单；
2. 深拷贝参数并冻结本次调用，捕获前台包名、Activity、revision 和动态目标证据；
3. `SafetyPolicy.assess()`，危险调用确认后同时复核原参数指纹；
4. 普通调用进入 retry guard 后执行；
5. 危险调用展示由网关生成的确认卡片；
6. 拒绝返回 `E_BLOCKED`，超时返回 `E_CONFIRM_TIMEOUT`；
7. 允许后重新读取上下文并重新解析动态目标；不一致返回 `E_STALE_REF`；
8. 校验通过才调用 handler；`ui_action`/`press_key` 的最终执行点消费已复核证据，并保证 handler 最多调用一次。

原 `ui_action` 内联确认逻辑移入统一门，避免双重弹窗。独立 MCP `confirm` 工具从工具面移除；确认能力只作为网关内部执行门存在，不允许“先确认一句自由文本，再执行另一件事”的松散协议。

`ConfirmOverlay.ask()` 以同步锁串行确认；悬浮窗权限、主线程调用、显示、等待、超时和清理任一环节失败都返回结构化错误并保持 fail-closed，不触达 executor。确认卡清理未完成时，即使用户已经点过“允许本次”也不得继续执行。

### 4.3 上下文绑定

不要求原始 revision 完全相等（悬浮窗本身可能引发无障碍窗口事件）。绑定规则：

- 普通 D 工具：前台包名和 Activity 必须一致；revision 进入审计。
- `ui_action(ref=...)`：确认后重新解析 ref；文本、描述、bounds 和来源必须与确认前一致。
- `press_key(enter)`：前台包名、Activity 与当前焦点输入节点标识必须一致（a11y 焦点不可得时的显式降级见 [IME 单命名空间降级门](2026-07-25-IME单命名空间降级门-design.md)）。

这比只比较 revision 更能区分“确认层自身造成的事件”与“底层页面/目标真的变了”。

## 5. 测试与验收

纯 JVM 单测（`SafetyGateTest`、`SafetyPolicyTest`）必须覆盖：

1. D 工具未经确认不执行；允许后只执行一次。
2. 拒绝、超时均不执行。
3. `press_key(enter)` 必须确认，`back/home/del` 不被误升 D。
4. “文件传输助手”页面上的“发送”仍必须确认。
5. 确认后工具参数、前台 App/Activity、UI 目标变化均不执行。
6. 普通 R/W 工具保持原行为。
7. 安全拒绝/超时不消耗 retry guard 失败次数。
8. 新 `Level.D` 工具无需自行写确认代码也会被统一拦截。

真机验收三件事：`press_key(enter)` 停在发送前并显示准确确认卡；拒绝后未发送、允许一次后只发送一次；确认期间切换页面或目标后动作因上下文失效被拒。真机只经受控派单通道执行，开发会话不直接操作手机；离线结果不得声称真机通过。

## 6. 非目标

- 不在本设计接入 Shizuku、通知层、IME 自动切换或 `ui_diff`。
- 不修改 `app_launch/share_file` 的后台启动兜底。
- 不实现通用授权令牌或跨会话授权。
- 不改变敏感 App 黑名单和支付/生物识别不可自动化边界。
