# 设计说明：危险动作统一硬门

- 日期：2026-07-19
- 状态：代码落地、离线验证通过；真机待验
- 范围：M1 执行网关 P0 安全修复

## 0. 落地状态（2026-07-19）

- `Level` 已从 MCP 注册层下沉到 `core`，风险等级成为统一安全策略的输入，不再只是工具描述元数据。
- `ToolRegistry.call()` 在任何 handler 前统一进入 `SafetyGate`；安全门深拷贝并冻结本次参数，确认后复核原参数指纹与当前 App/Activity/目标上下文，最终执行点仍使用复核后的目标证据。
- `ConfirmOverlay.ask()` 串行处理确认卡；主线程误用、权限缺失、显示/等待/超时/移除异常均结构化失败并保持 fail-closed，不触达 executor。
- 离线验证已通过 19 条 JVM 单测（`SafetyGate` 12 条、`SafetyPolicy` 7 条）和 gateway debug 构建；尚未连接手机执行本设计的三项真机 smoke。

## 1. 问题与根因

项目铁律要求发送、支付、删除类操作永远在临界动作前停下，人工确认后才能继续。但当前网关没有统一执行这条约束：

1. `ToolSpec.level` 只用于描述工具风险，`ToolRegistry.call()` 调用 handler 前不检查 `Level.D`。
2. `ui_action(click/long_click)` 仅在自身实现里按危险词触发悬浮窗，其他执行通道不会经过这段逻辑。
3. `press_key(enter)` 被登记为普通写操作，却会优先执行 `ACTION_IME_ENTER`，再降级到 `IME_ACTION_SEND`，在聊天输入框中可能直接发送。
4. 独立 `confirm(action_desc)` 只返回布尔值，没有把批准绑定到具体工具、参数和当前页面；它不能构成后续动作的机械授权。
5. `safety.json` 的“文件传输助手”发送白名单与当前项目铁律冲突。P0 以铁律为准：所有发送动作都确认，不保留执行器侧免确认例外。

根因不是某一个工具漏写 `if`，而是风险等级、动态风险识别、确认 UI 和实际 handler 分散在不同层，缺少一个所有工具都绕不过的执行门。

## 2. 安全不变量

修复后必须始终成立：

1. 所有 `Level.D` 工具在 handler 执行前都经过统一确认。
2. `Level.W` 工具可按参数和目标动态升级为危险动作；首批覆盖 `press_key(enter)` 与 `ui_action` 的发送/支付/删除目标。
3. 未确认、拒绝、超时、确认后上下文失效时，handler 调用次数必须为 0。
4. 一次确认只授权当前这一次调用，不生成可重放的通用令牌。
5. 确认卡片展示由网关生成的实际工具、关键参数、前台 App/Activity 和目标控件证据，不能只展示模型自由填写的描述。
6. 确认返回后重新校验前台 App/Activity；带 `ref` 的 UI 动作还要重新解析目标并核对文本、描述和 bounds。目标变化即返回 `E_STALE_REF`，不得执行。
7. 危险动作的请求、确认结果、上下文校验和最终结果全部写入审计；新增安全审计字段只记录判定结果、参数指纹和必要目标证据，不额外复制消息正文等敏感参数。现有审计参数脱敏不在本任务扩展范围内。
8. 安全失败不得进入重试守卫的“同法失败次数”，避免用户拒绝或等待确认被误判为执行故障。

## 3. 方案比较

### 方案 A：统一路由内联确认并执行（采用）

`ToolRegistry.call()` 在 handler 前计算风险；危险调用阻塞等待 `ConfirmOverlay`。用户允许且上下文复核通过后，同一次调用立即执行 handler。

优点：授权天然绑定当前工具和参数；没有令牌、缓存或重放面；对未来 `notification_reply` 等 D 工具自动生效。缺点：工具调用会等待人工操作；带外确认仍需 harness 后续收口。

### 方案 B：显式一次性授权令牌

先调用结构化 `confirm(tool, args)` 获得短时令牌，再把令牌交给危险工具。

优点：两阶段在协议上可见。缺点：需要令牌存储、规范化参数、过期/消费/重放防护，并修改所有危险工具 schema；P0 引入的状态面过大。

### 方案 C：逐工具补确认

只给 `press_key(enter)` 增加悬浮窗，保留 `ui_action` 现状。

改动最小，但无法保证未来 D 工具和其他通道不再漏接，不能解决根因，因此拒绝。

## 4. 组件设计

### 4.1 `SafetyPolicy`：纯判定层

已新增纯 Kotlin 判定组件，并把 `Level` 下沉到 `core`。组件输入为工具名、静态等级、冻结参数和动态目标证据，输出：

- `Allowed`
- `ConfirmationRequired(actionSummary, evidence)`
- `Blocked(code, reason)`

首批规则：

- `Level.D`：始终 `ConfirmationRequired`。
- `press_key(key=enter)`：始终按“可能发送/提交当前输入内容”确认；其他按键保持原等级。
- `ui_action(click|long_click)`：目标命中发送、支付、删除、账号/安装等词表时确认；发送词不再因“文件传输助手”上下文免确认。
- 敏感 App 黑名单继续先于确认执行，不能通过人工确认绕过银行/证券默认拒进。

### 4.2 `SafetyGate`：统一执行门

已落地的统一调用顺序：

1. 校验工具存在、敏感 App 黑名单；
2. 深拷贝参数并冻结本次调用，捕获前台包名、Activity、revision 和动态目标证据；
3. `SafetyPolicy.assess()`，危险调用确认后同时复核原参数指纹；
4. 普通调用进入 retry guard 后执行；
5. 危险调用展示由网关生成的确认卡片；
6. 拒绝返回 `E_BLOCKED`，超时返回 `E_CONFIRM_TIMEOUT`；
7. 允许后重新读取上下文并重新解析动态目标；不一致返回 `E_STALE_REF`；
8. 校验通过才调用 handler；`ui_action`/`press_key` 的最终执行点消费已复核证据，并保证 handler 最多调用一次。

原 `ui_action` 内联确认逻辑移入统一门，避免双重弹窗。独立 MCP `confirm` 工具从工具面移除；确认能力保留为网关内部执行门，不再允许“先确认一句自由文本，再执行另一件事”的松散协议。

`ConfirmOverlay.ask()` 以同步锁串行确认；悬浮窗权限、主线程调用、显示、等待、超时和清理任一环节失败都会返回结构化错误。确认卡清理未完成时，即使用户已经点过“允许本次”也不得继续执行。

### 4.3 上下文绑定

不盲目要求原始 revision 完全相等：悬浮窗本身可能引发无障碍窗口事件。绑定规则为：

- 普通 D 工具：前台包名和 Activity 必须一致；revision 进入审计。
- `ui_action(ref=...)`：确认后重新解析 ref；文本、描述、bounds 和来源必须与确认前一致。
- `press_key(enter)`：前台包名、Activity 与当前焦点输入节点标识必须一致。

这比只比较 revision 更能区分“确认层自身造成的事件”与“底层页面/目标真的变了”。

## 5. 测试与验收

实现按先失败测试、后代码的顺序落地。现有 19 条纯 JVM 单测（`SafetyGateTest` 12 条、`SafetyPolicyTest` 7 条）覆盖：

1. D 工具未经确认不执行；允许后只执行一次。
2. 拒绝、超时均不执行。
3. `press_key(enter)` 必须确认，`back/home/del` 不被误升 D。
4. “文件传输助手”页面上的“发送”仍必须确认。
5. 确认后工具参数变化、前台 App/Activity 变化、UI 目标变化均不执行。
6. 普通 R/W 工具保持原行为。
7. 安全拒绝/超时不消耗 retry guard 失败次数。
8. `Level.D` 新工具无需自行写确认代码也会被统一拦截。

离线测试与 Android debug 构建已通过。真机仍待验，只验证三件事：

1. 微信输入框调用 `press_key(enter)` 时停在发送前并显示准确确认卡片；
2. 拒绝后消息未发送；允许一次后只发送一次；
3. 确认期间切换页面或目标后，动作因上下文失效被拒绝。

真机阶段必须由用户连接设备后，通过 `scripts/dispatch.ps1` 的受控派单通道执行；开发会话不直接操作手机。由于当前 wrapper 仍未正式接入 gateway，若届时该阻塞仍在，应先完成最小 gateway executor 接线，不以手工直控绕过。
