## S1 ⭐ 微信节点树可读性（决定 OCR 融合排期）

探针配置确认拉满：`flagIncludeNotImportantViews|flagReportViewIds|flagRetrieveInteractiveWindows` + `canRetrieveWindowContent=true`。

| 页面态 | uiautomator | probe 自研 a11y | 微信 window.root |
|---|---|---|---|
| 聊天列表页 | nodes=1（恒空） | 总 nodes=20 / withText=3 | **null**（bounds 全 0） |
| 会话页（文件传输助手） | nodes=1 | 总 nodes=20 / withText=3 | **null** |
| 键盘弹出态 | — | 总 nodes=36 | **null** |

- 三态下微信主窗口（`window id=138 type=1 pkg=com.tencent.mm`）都出现在 windows 列表（说明 `flagRetrieveInteractiveWindows` 生效），但 `window.root` 恒为 **null**——20 个可读节点全是 vivo 系统 UI（灵动岛 systemuiplugin / 上滑条 upslide / 悬浮球 floatingball），**微信自身贡献 0 个可读节点**。
- **复现并强化 M0 结论**：不仅 uiautomator 通道空，自研 a11y（微信抢红包类工具的旁证）也读不到——微信对无障碍内容做了屏蔽（window 可见、content 不可取）。
- ✅ **键盘感知通道成立**：键盘弹出时 windows 新增 `id=123 type=2（TYPE_INPUT_METHOD）pkg=com.baidu.input_vivo bounds=(0,1825-1260,2800)`。即便 app 内容不可读，**键盘弹出/收起可通过 windows 列表有无 type=2 判定**（M0 两次误触的感知面得到验证）。多出的 16 节点是百度输入法自身的按键树（可读，但非目标内容）。

**判据落点 = ❌ 不可读分支**：OCR 融合层进 M1a 且为微信类任务主通道；spec §11 决策点「OCR 融合是否提前进 M1a」拍板 → **提前进 M1a**；spec §2 冲突点 #10「自研 a11y 能读微信则收益上修」的乐观分支**否定**；§12 微信类（任务 2/4）估算取上限。

| 页面 | takeScreenshot | ocr | lines |
|---|---|---|---|

- 噪声：会话内嵌的小红书长截图产生一堆 conf<0.3 的二次文字乱码——用 conf 阈值（>0.5）过滤即可，不影响主体控件。
- 小问题：数字 `0` 被识成字母 `O`（M0→MO）——ML Kit 中文模型已知，融合层对 ASCII 场景可加规则修正。
- **京东深色首页补测（一发覆盖重动画页+深色两点）**：69 行中 60 行 conf>0.5，价格（¥14.4/¥3681/¥23499）、入口（秒杀/拍拍二手/爱回收/学生专区）、促销文案全命中，**深色模式不塌方** ✅。940ms 属重内容页（69 行密集文本）的正常放大，仍低于 1.5s 升级线；轻页面 ~450ms。个别形近字错（补贴价→补站价、清凉季→濱凉季），bbox 与语义无碍。
- **达标**：ML Kit bundled 中文起步够用，PaddleOCR 升级位暂不启用。

## S4 截图延迟与节流

- 单发 `takeScreenshot` **32–37ms**，远优于 ≤500ms 判据。
- 节流：连发两次（间隔 ~400ms），第二次**未报** `ERROR_TAKE_SCREENSHOT_INTERVAL_TIME_SHORT`，而是 `takeScreenshot` 从 32ms 涨到 **759ms**（系统内部排队/软节流，延迟返回但成功）；冷却 2s 后单发回落 37ms，确认 759ms 系节流所致。
- **与 runbook 预期不同**：预期「第二次 SHOT failed」，实测 Android16/OriginOS6 是**软节流（拖延 ~750ms）而非硬失败**。网关 `E_RATE_LIMITED` 冷却窗口参考 **~800ms**（连发保护按此设间隔，或容忍单次 ~750ms 延迟）。

## 意外发现（回填 vivo-originos.md）

- **OriginOS6 下 adb `settings put secure` 可开启无障碍服务，但不持久**：`settings put secure enabled_accessibility_services <svc>` + `settings put secure accessibility_enabled 1` 两键同置，**异步生效（~3s）**，之后探针 `probe connected`、广播 DUMP 正常。注意：写入是异步的，同命令内立即 `get` 读到空属正常（下一次读即有）。⚠️ **数小时后被系统撤销**（22:22 正常 → 01:24 两键被清、服务进程没了；具体触发时点未标定，疑似午夜策略/空闲清理）。开发期对策：脚本里每次跑测前重放两条 put（重放后立刻恢复）；持久启用仍需设置 UI 手动开 + 电池白名单。
- **`input tap` 点无障碍开关无效**：vivo 无障碍详情页的启用开关不响应 `input tap`（反自动化）——但上面的 settings put 路径可绕过，开发期开探针/网关无障碍**无需手动点开关**。
- `am start -a android.settings.ACCESSIBILITY_SETTINGS` ✅ 可靠带到前台（sys-cli.md §4 的 🔵 待验证 → 转正）。

### 真机首跑抓到 2 个网关真 bug（均已修 + 重编验证）

1. **MainActivity 启动即崩** `SecurityException: Settings key <enabled_input_methods> is only readable to apps with targetSdkVersion ≤ 33`——`Gateway.imeEnabled()` 直读 `Settings.Secure.ENABLED_INPUT_METHODS`，targetSdk35 被系统封禁。**修**：改用 `InputMethodManager.enabledInputMethodList` 判断（[Gateway.kt:52](../../app/gateway/src/main/java/dev/magina/gateway/Gateway.kt)）。
2. **system_get_state(wifi) 报** `SecurityException: ...ACCESS_WIFI_STATE`——`WifiManager.isWifiEnabled` 需该权限，Manifest 漏声明。**修**：补 `ACCESS_WIFI_STATE` + `ACCESS_NETWORK_STATE`（[AndroidManifest.xml](../../app/gateway/src/main/AndroidManifest.xml)）。

> 另记一个**非网关问题**：PowerShell smoke 脚本里误用 `$args` 做函数参数名（PS 保留的自动变量），导致 `arguments` 序列化成空、带参工具全报 `E_INTERNAL: No value for key`。改名即解——网关的 McpServer 参数提取（`params.optJSONObject("arguments")`）本身正确。排障时先怀疑了网关，核对代码后定位到脚本坑。

### 大脑联调必经通道去险补测（PC smoke，01:55–02:08）

联调前把三个必经但未验的通道先安全验掉（不碰真危险动作），避免联调半路撞未知：

- **`ui_action` 点击** ✅：`ui_find(蓝牙)` → `ui_action(click)` → `done:true`，`foreground_app` 确认进 `BluetoothSettingsActivity`。点击前二次校验 + 页面跳转链完整。
- **`confirm` 悬浮窗 —— 前台 ✅ / 后台 ⚠️被 vivo 拦**（**重要，影响联调**）：网关**在前台**时卡片正常弹出（「⚠ Agent 请求执行危险操作」+ 拒绝/允许本次），点「允许本次」→ 后台调用返回 `{confirmed:true}`，弹窗→点击→响应闭环完整。但网关**在后台**（前台是别的 app）时，OriginOS **静默拦截 overlay `addView`**——代码 `ConfirmOverlay` 的 `main.post{addView}` 线程模型正确、不抛异常，但窗口不显示，`confirm` 等满 60s → `E_CONFIRM_TIMEOUT` + 带外 `[AWAIT_CONFIRM]`。**根因：vivo「后台弹出界面」是独立权限，`SYSTEM_ALERT_WINDOW` 不覆盖它**。**对大脑联调的影响**：跑真实任务时网关必然在后台，危险动作的**带内悬浮窗弹不出，只能走带外两段式**（harness 蓝牙版已验 ✅，路径可用但体验降级）。解决方向：给网关授 vivo「后台弹出界面」权限（用户在手机管家/权限设置，或 appops 若可），或大脑协议在 vivo 上对危险动作直接走带外。
- **`share_file` 三级降级** ✅：`media_query(screenshot)` 取最新 uri → `share_file(target=微信)` → `channel=direct_component` 拉起微信 `MsgRetransmitUI` 选择聊天页（ShareImgUI 直达命中）。**首发遇微信冷启动 splash 闪回**（`foreground_verified` 只验到包名级、抓到 `WeChatSplashActivity` 即判 true——验证略宽松），热启动第二发稳定停留选择页。未点发送，零副作用。→ 观察点：share_file 的 `foreground_verified` 宜验到 ShareImgUI/选择页 activity 而非仅包名，避免 splash 闪回误判成功。

剩余未覆盖（留大脑联调）：微信树空场景 `type_text` 走 IME+OCR 降级（S1 树空下 readback 预期 null，验降级分支）。
