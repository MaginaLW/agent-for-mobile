# 阻塞处理调查与收尾

日期：2026-11-12。调查基线 `f1dd5e982c628a44b3143db5bdde5b7eb1fddfb3`。本轮按用户要求调查处理办法后收尾，继续以现有微信、PA2553和原生多窗为边界。只查公开资料、固定源码和既有项目文件；未连接设备、采图、发Intent、安装、提权、联系第三方、运行测试或修改产品代码。本报告是调查结果及待评审建议，不修改现行合同、验收判据、许可或生产行为。

## 结论与建议

此前“只有平台/目标App合作来源才能继续”的表述过窄：它描述了满足现行强来源合同的一种可能方向，不是所有工程方案的不可能性结论。现有权限下还可评估单帧视觉方案，以及更贴合原产品语义的R5验收设计；两者均不是已经通过现行门禁。

建议下次先做两项离线评审：视觉侧比较“同一合成帧内的可观察证据”与原生身份/跨阶段有效性的要求；R5侧分清“未获正向验证”与“整个时间窗从未落地”。先明确可实现的接受/拒绝条件、保留保证和残余风险，再决定是否值得实施。今天只交付这份调查，不自动启动下一阶段。

## 视觉来源：可选路线及实际收益

| 路线 | 能处理什么 | 仍不能证明 / 结论 |
|---|---|---|
| 同一张合成整屏图作为唯一视觉事实源 | 同一buffer中判断pane、标题/消息/编辑区及可见键盘/遮挡，减少不同采集结果的视觉拼接；复用现有单次采集、区域定义和内存所有权 | 不证明原生window归属、实际输入连接、不可见触摸拦截、图像到输入坐标或截图后的布局不变；优先离线评审，尚未准入 |
| Android14+ MediaProjection单应用共享 | 用户选择内容，保留原windowing mode；有捕获内容resize/stop回调，可管理尺寸和隐私范围 | 不给共同layout epoch或带版本的window→屏幕变换；应用共享排除系统UI，不能默认观察到确认卡/全部遮挡；增加系统同意、前台服务及会话管理成本，后置 |
| UI Automator稳定性等待 | 周期比较节点/可选图像，减少已观测动画或布局变化带来的不稳定 | 官方明确不保证完全idle，API也提示非确定性；不是采集/动作原子屏障，不因树opaque而自动有效 |
| scrcpy坐标映射参考 | 固定源码提供显式video→device矩阵，视频尺寸不符时拒绝位置；可参考缩放/旋转守卫 | server以shell运行并使用隐藏接口，不能原样当作普通gateway能力；矩阵/尺寸检查不是原生身份或epoch证明，不为此引入新依赖/控制通道 |

MediaProjection的visibility=true仅表示捕获内容至少部分可见，不证明无遮挡；Image/SurfaceTexture时间戳的含义与时基依生产者而定，不能直接当作与uptime或其他来源可比的全局采集时刻。texture采样矩阵也不是OS窗口到物理屏幕的同代变换。

单帧路线确实减少视觉分量之间的跨帧问题，但不能把“同一图像内一致”改称“原生窗口、树、IME及执行瞬间全部同代”。模型可能错框、错认同名会话，透明窗口可能拦触，识别后到动作前仍有状态变化风险。原生清单缺失/矛盾应继续拒绝；不因它只作守卫就忽略unknown、IME或身份要求。

未来若继续评审，应逐项比较现行[视觉合同§1、§3–§4、§6–§7](../specs/2026-11-01-平板window-pane视觉证据合同-design.md)：原生window/pane绑定、区域语义、图→屏幕变换、跨阶段失效、输入连接、确认卡可见可触、隐私及后验。不能只删除约束或自报一个epoch。第一条可能的验证链限只读感知与拒绝结果，不包含输入或动作；只读通过也不能放行T-L1/P0。新的帧、系统同意或设备验证仍需固定候选和对应许可。

## R5：先区分生产错误语义与验收证明强度

原[M1产品协议](../specs/2026-07-17-M1执行网关-design.md)的`intent_send`规定：指定目标时等待正向前台证据，超时/无证据返回`E_VERIFY_FAIL`；未指定目标如实报告未验证。[09-27原R5标准](2026-09-27-项目审查与待办.md)要求失败报错及启动未抛异常但未落地的反例，没有明文要求系统接收与全时段从未出现的联合证明。

当前[IntentTools](../../app/gateway/src/main/java/dev/magina/gateway/tools/IntentTools.kt)的判据为目标已指定且`foregroundVerified != true`，文案也是未能确认目标前台；[SystemTools](../../app/gateway/src/main/java/dev/magina/gateway/tools/SystemTools.kt)无无障碍实例或未取得正向命中即返回false。因此`E_VERIFY_FAIL`不承诺目标从未收到或从未出现。当前纯判据测试只证明分支语义，不是真机验收。

唯一请求关联、独立系统接收、实际验证窗口和完整覆盖，是[后期强取证设计](2026-11-01-R5独立取证可行性核定.md)及[Mika任务4](../specs/2026-11-01-Mika借鉴与阻塞解阻-design.md)的现行要求。本轮没有取消它们或关闭R5。可考虑的解阻方向是未来显式重审验收设计，验证真实原gateway调用在未获正向证据时应报错、不能误报verified；这可以不改变生产协议，但必须说明保留哪些原反例、哪些事实不再声称，并完成适用评审。

瞬时独立观察只能证明当时不匹配，不能推定全窗口未出现。任何重审后的真实调用验收仍需固定候选、原App身份/入口、一次调用及响应/审计绑定、实际观测范围和错误原因；不能拿未触达、参数无效或原生调用错误冒充所需反例。正向落地、无接收方、未知目标等结论分开核定。

| 额外系统路线 | 调查结果与处理建议 |
|---|---|
| `startActivityAndWait` / `am start -W` | WaitResult是对应同步调用的系统返回对象，但含UNKNOWN、复用零耗时、cleanup无效时长等分支，不证明业务页面正确。`-W`由shell身份发起新调用，不能旁观或回填原gateway路径；隐藏接口也不等于普通App可合法直接调用。保留为可能的新集成研究，不用于凑当前验收 |
| ActivityController / `am monitor` | 隐藏测试控制接口，需SET_ACTIVITY_WATCHER，注册单个全局controller且能拒绝启动/恢复；回调是尝试阶段，缺请求级关联，默认monitor输出只含包名。不是无干扰的只读完成回执，不建议当前R5采用 |
