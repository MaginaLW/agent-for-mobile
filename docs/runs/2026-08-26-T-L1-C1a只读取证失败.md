## 根因与 A 道修复边界

### 1. Windows stdin 破坏 T0 原始 bytes

宿主 T0 为 23,865 bytes，包含 747 个 CRLF，artifact SHA-256 为 `43d952...`。原 runner 使用普通
`adb shell content write`；Windows ADB shell stdin 路径把全部 CRLF 归一为 LF，provider 声明的 hash 变为
`f9d548...`，且它精确等于“只做 CRLF→LF”后的宿主 bytes hash。Kotlin factory/context 均复制输入 bytes，
全零同长度样本 hash 也不同，因此不是 app 内部清零或 aliasing。

修复限定为 T0 write 使用 `adb exec-in content write` 的 binary stdin，并传通过 closed grammar 的 raw
canonical URI。不能用 `exec-out`，因为它不向远端发送 stdin；也不能给 `exec-in` URI 预置字面 POSIX 单引号，
因为该路径会自行 escape argv。status/c1/c2/result/abort 仍使用 `adb shell content read` 与远端 POSIX 引号。
write 不提供远端 ACK，首次 status 的 bounded wait 继续作为认证/完成边界。

### 2. 静态页 raw revision 15/15 被误作采集顺序失败

页面保持静态时没有新的无障碍事件，两帧 raw event revision 合法地同为 15。既有 producer/validator 要求
下一帧 observation revision 严格递增；observation 内部记录 token/capture ID 严格有序且间隔 1982.304 ms，
但这些记录不构成 trusted origin，最终仍被标为 `capture_order_invalid`。

六个 producer/T0 baseline blob 保持原样。修复只在 debug-only C1a adapter 生成可逆 logical marker：

```text
logical revision = raw event revision + capture token ordinal
```

其中 c1/c2 ordinal 固定为 1/2，可用 token 还原 raw。相同或递增 raw revision 可表达严格采集顺序；raw
下降、未知 token、溢出继续阻断；同一帧读取期间 raw event 变化仍使 before/after 不相等并 fail closed。

### 3. 真实 diagnostic blocker 不随 transport/order 修复消失

下列七项来自真实 window/pane/node/region/focus 观察，必须继续保留：
