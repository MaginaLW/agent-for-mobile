# PA2553 横屏微信「文件传输助手」就位

本次只做导航和输入焦点核对。保留全部草稿。不要输入、发送、按键、切换输入法、调取图片、读取消息或抄录草稿。遇到阻塞或任一工具报错，立即以失败结束，不换路、不重试。

1. 读取 `foreground_app`。已在微信则沿用。已确认是解锁后的系统桌面才可调用一次 `app_launch(name="com.tencent.mm")`，随后复核微信已取得前台。锁屏、其他应用、身份不明或遮挡时停止。
2. 用 `foreground_app` 返回的 `windows` 核对两个横向并排的微信应用窗口及其边界、窗口 ID、活动和焦点。只接受 `window_topology=same_app_multi`。用 `ui_find(text="文件传输助手", scroll_search=false)` 定向查找，按完整文字、位置和窗口归属识别右窗顶部标题。
3. 若右窗已活动并持有焦点、顶部标题精确匹配，直接进入第 4 步，即使查找只返回这个标题也已完成导航，导航点击为零。只有需要导航时才核对左窗列表行；仅可点击左窗里唯一、完整同名的具名会话行一次，用本次查找的 ref 和 `ui_action(action="click")`。如果网关复核失败即结束。切窗后用新的前台读数和定向查找重验右窗标题、活动和焦点，丢弃旧 ref。
4. 读取 `keyboard_state`，再用 `ui_find(role="input", scroll_search=false)` 核对右窗底部编辑栏。仅接受带原生可编辑标志 E、已启用、边框完全位于该右窗编辑行内的唯一输入框；排除键盘、会话消息、语音控件和「发送」。已经具有输入焦点时不点。否则只可对该编辑框的新 ref 调用一次 `ui_action(action="click")`。禁止对无引用的空白区域、文字提示或其他控件试点。
5. 最后重读右窗焦点、标题、键盘状态与输入框。只有同一右窗编辑框带 E 和 F、`focused_input_id` 非空且 `focused_input_bounds` 与其边框一致，才报告执行器已就位。键盘显隐单独报告。宿主另外核对系统焦点与输入法目标窗口。

按站规终态格式报告起点、启动次数、导航与编辑栏各自的点击次数、右窗和输入焦点、键盘状态、是否出现确认卡及首个阻塞。只报告证据类别和结果，省略草稿、联系人列表和消息正文。
